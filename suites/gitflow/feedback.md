## v0.6.0 历史分支清理 /gitflow:clean（2026-11-04）

- 来源：用户提出，随着缺陷与需求累积，任务分支越来越多，希望手动清理某个时间之外（一个月或两周）的本地与远端分支。分支不能随便删，所以只找用户名开头、由 `/gitflow:start` 创建的分支；找到后列出每个分支的最后提交简要信息，**不弹窗**，由用户看清单后回复“全部清理 / 保留某个分支”，明确指令后才执行删除。
- 采纳：
  - 新增 `/gitflow:clean`，默认 30 天，`--days 14` 可缩短到两周
  - 只匹配规范化用户名前缀 `<user>/`；不符合 `branch_pattern` 的分支仍列出并标注“非标准命名”
  - 本地与远端分别按 tip 时间判断，另一侧较新时标注“较新，不删除”
  - 第一阶段只列清单并等待；第二阶段按明确指令删除，删除前重新 fetch 并复核 SHA
  - 排除当前分支、保护分支与任何 worktree 检出中的分支
  - 多仓库用 `--repo` / `--repos` 显式扫描；单个仓库 fetch 失败不产生候选并记录，其他仓库继续
- 同批修正：用户实测 MR 描述时发现 `## 自测情况` 固定输出“单元测试通过（如有）”，没有单元测试时仍留下空勾选项。改为按本次改动是否涉及测试文件裁剪，没有测试改动就删除该行，仓库模板中的同类空占位也一并删除。
- 决策：
  - 不做扫描后自动删除、不弹窗确认：用户要求先看清单再下指令；自动删除无法区分“旧分支”与“需保留的长期分支”
  - 不按环境链过滤：旧版本环境可能已下线，按 `active` 过滤会漏掉最需要清理的分支；用户名前缀已足够限定个人任务分支
  - 用 `branch -D` 而非 `-d`：squash 合并后的任务分支通常不是环境分支的祖先，`-d` 会误判为未合并；`-D` 仅在用户明确指令后使用
  - 不检查 GitLab MR 状态：glab 查询成本高且状态可能滞后，改为在输出中提示用户自行确认
  - 不提供 `--dry-run`：第一阶段本身只读，无副作用
- 待实测：
  - Windows 下 `date +%s` 与 `for-each-ref` 的 Unix 时间字段是否与 Git 版本兼容
  - 多 worktree 场景的 `worktree list --porcelain` 解析是否完整
  - “保留 N / 只删 N / 只删本地或远端”等指令解析是否稳定
  - 远端分支被 GitLab 分支保护拒绝删除时的错误输出是否清楚

## v0.5.1 提升不等待源环境合并 / MR 原始链接（2026-11-04）

- 来源：用户实测后提出两点：
  - `/gitflow:promote` 不用等待之前的分支是否已经 merged，直接创建新分支并合并即可；源环境 MR 与提升 MR 不应相互阻塞
  - `/gitflow:merge`、`/gitflow:promote` 完成后的 MR 链接不要带中文（如全角括号），浏览器点击时会被截断导致打不开；链接直接用 MR 本身的 URL，不加过多描述
- 采纳：
  - 移除“源分支已合入源环境”的校验与 merge/squash 提交识别；源 tip 只比较本地与远端，分叉则停摆
  - 默认清单改为 `rev-list --reverse --no-merges --right-only --cherry-pick <target>...<source-tip>`，任意合并方式（未合并/merge/squash/rebase/fast-forward）都可用
  - `--commits` 清单保留祖先过滤 + `git cherry` 补丁等价过滤
  - MR 链接单独一行输出原始 URL；去掉中文、全角括号与说明文字
- 决策：
  - 保留 cherry-pick 而非普通 merge：目标环境落后时，直接 merge 源任务分支会把低环境提交一起带入
  - 不等待合并：链式模型只要求提交内容一致，不要求源环境先接收；两侧 MR 各自 review
- 待实测：
  - 源环境 MR 未合并时执行 promote，目标环境清单是否只包含本任务提交
  - 目标环境落后于源环境时，对称差清单是否混入低环境同步提交；`--dry-run` 提示是否足够
  - 源环境 squash/rebase 后，提升重放与最终内容是否一致
  - MR URL 在终端/VSCode 中点击是否完整

## v0.5.0 环境提升 /gitflow:promote（2026-11-04）

- 来源：用户实测 `/gitflow:merge` 成功：`pro-pcb/jiangshun/fix/4.1-CHML-151021` 自动创建 MR 并合入 `pro-pcb/4.1`；希望继续提升到 `dev`，并给出流程——按 `/gitflow:start` 从目标环境新建分支、逐一 cherry-pick 本次合并涉及的提交（冲突尽量解决，解决不了停摆）、再走 `/gitflow:merge`；多仓库则逐一处理。用户认为每个版本新建分支互不干扰，也方便解决冲突。
- 采纳：
  - 新增 `/gitflow:promote [环境]`，按用户描述的顺序实现；目标环境缺省为链中下一个 `active`，也可显式指定
  - 提交识别优先 merge 提交（父提交包含源分支 tip），其次按工单号找唯一 squash 提交，最后要求 `--commits`
  - cherry-pick 冲突在 core §5.5 限额内自动解决并 `--continue`，不逐次确认；超限即停摆并保留现场
  - 多仓库用 `--repos` 显式列出，兄弟仓库用临时 worktree，避免切换主工作区；失败仓库之间隔离
  - MR 复用 `/gitflow:merge` 流程，描述注明“从 <源环境> 提升”
- 决策：
  - 不采用“环境分支 → 环境分支”MR：源环境是保护分支，提升与日常合入会混在一条历史线，冲突无法隔离到单个版本
  - 不自动提升同名分支的兄弟仓库：延续“跨仓库写操作必须显式”的安全边界
  - 自动解决不加入逐次确认：用户明确希望冲突尽量自动处理，解决记录统一在结果中输出，由 MR review 兜底
  - `glab` 统一在仓库根目录执行，顺带修复 merge 在 `--repo` 模式下可能操作错仓库的问题
- 待实测：
  - GitLab 实际使用的合并方式（merge / squash / fast-forward）下，提交识别是否命中；不命中时 `--commits` 提示是否足够清楚
  - 源分支内部含 merge 提交时，跳过的冲突解决改动是否会造成提升后行为差异
  - 多仓库临时 worktree 的创建/清理在 Windows 路径与权限下是否稳定
  - 限额内自动解决的结果是否可接受，是否需要把解决摘要也写入 MR 描述
  - 提升分支命名（同 user/type/ticket，仅换环境）是否与团队习惯一致

## v0.4.8 MR 模板可读性修正（2026-11-04）

- 来源：用户实测 `/gitflow:merge` 生成的 MR 描述后提出：
  - 关联工单有链接和标题时应该用链接形式，方便点击
  - `## 合并链路` 下的段落需要换行，否则提交后全在一行
  - 不需要 `## 审核人` 章节：`/assign_reviewer` 提交后被自动执行并消失，只剩空标题
- 采纳：
  - `{{ticket}}` 有链接时按 `[单号 标题](链接)` 填写，仅链接时 `[单号](链接)`，无链接才用纯文本；多工单每行一个
  - 合并链路三行之间各留空行；自测项默认未勾选
  - 删除审核人标题，`/assign_reviewer` 直接放描述末尾；审核人为空时删除整行
- 决策：
  - 链接格式由命令在生成描述时统一处理，不要求仓库模板自行拼接
  - 保留 `/assign_reviewer` 快速指令（而非只依赖 glab `--reviewer`），因为它在 web 端编辑 MR 时也有用；只是不再给它单独标题
- 待实测：
  - GitLab 对 `[单号 标题](链接)` 的渲染与点击跳转
  - 合并链路空行在提交后的实际换行效果
  - 无审核人时描述末尾是否干净

## v0.4.7 多仓库改动不打断、同名分支自动提交（2026-11-04）

- 来源：在 pro-pcb 执行 `/gitflow:commit` 时，其他仓库里自己改的其他任务代码会触发“是否处理其他仓库”的弹窗，与本次开发无关，造成干扰。用户明确：其他仓库有变动不弹窗、默认不提交；只有其他仓库当前分支与当前仓库同名时才提交，说明是跨仓库处理同一任务；否则一律不处理。
- 采纳：
  - 检测改为按当前检出分支名分类，不再询问用户
  - commit 缺省模式：操作仓库成功后，对同名分支且有未提交改动的兄弟仓库自动执行同一流水线并推送
  - 显式 `--repo` 只处理指定仓库；不同分支改动只在摘要列出
  - sync / merge 只提示同任务未提交改动，不停摆
- 决策：
  - 分支名相同是团队既有的任务对齐约定（`/gitflow:start --repos` 也用它），比分析改动内容更确定、可预测
  - 同名仓库若状态不安全（detached、merge/rebase 中、保护分支、敏感文件）则跳过，不为了“全自动”冒险
  - 兄弟仓库失败不回滚、不阻断主仓库：提交流水线不是事务，回滚可能破坏用户编辑
- 待实测：
  - 多仓库同时提交时 commit-draft 生成的 scope/message 是否合理
  - 同名分支混入无关改动时用户是否能及时从摘要发现
  - 兄弟仓库推送失败/无上游时的提示是否足够清楚
  - 大工作区（5+ 仓库）检测与多仓库提交流水线的耗时

## v0.4.6 提交流水线先修乱码再格式化（2026-11-04）

- 来源：`/gitflow:commit` 实测时提出，先格式化再检查乱码会导致乱码修复又改到格式，应先检查/修复乱码，再执行格式化。
- 采纳：流水线调整为 `git add -A` → mojibake-fixer → format-keeper → `git add -A` → commit-draft → commit → push；命令步骤、停摆顺序、输出示例与文档同步。
- 决策：乱码修复是文本内容级改动，可能改变行长、字符宽度与注释对齐；格式化作为最后一道归一化步骤，能覆盖前序改动引入的格式偏差。反之先格式化则可能被后续修复破坏。
- 待实测：
  - 含中文/替换字符的长行在修复后是否被格式化为预期排版
  - 乱码修复与格式化各自触发的 `git add -A` 是否会造成暂存区遗漏或重复
  - 格式化失败时，已完成的乱码修复是否保留且可回滚/重试

## v0.4.5 init 非交互与严格版本号（2026-11-04）

- 来源：`/gitflow:init` 实测时遇到未解析映射、环境链里是否保留 `3.2.0918` 这类条目等决策点，希望不弹窗、不询问，AI 按推荐方案直接创建/更新配置，最后有问题再调整；并明确版本号只保留「数字.数字」结构，`dev`/`main` 等环境名除外，因此 `3.2.0918` 直接排除。
- 采纳：
  - init 全程不询问：链级增删、未解析映射、`active`/`default_env` 修正都不再确认，统一写入摘要后落盘
  - 未解析映射只有唯一候选时自动映射；多候选或无候选留空并列出候选，不猜测
  - 版本号判定收紧为 `^\d+\.\d+$`；多段数字探测时排除、已有 `chain` 自动剔除、显式 `--envs` 报错
  - 没有候选时写入占位链 `["dev"]` 并提示，不再停摆
  - 保留仓库的过期 `envs` 键自动补链或删除；候选时间读取失败只排除候选；停摆条件只保留真正的错误
- 决策：
  - 交互成本前移会打断多仓库初始化流程；配置是个人文件，用户看到摘要后直接编辑比逐项确认更快
  - 自动映射只在唯一候选时执行：错映射到错误环境比留空更危险，留空由后续命令停摆兜底
  - 多段数字版本号不是环境版本：`3.2.0918` 更像构建号，保留会污染链排序与提升语义
  - 占位链 `dev` 是已知安全默认：多数团队把 `dev` 作为链顶；不符合时用户手工调整
- 待实测：
  - 在 pro-ui / pro-pcb 等真实仓库中，唯一候选自动映射的命中率
  - 多候选留空后摘要列出候选的可读性，以及用户手工补 `envs` 的成本
  - 链级漂移自动增删是否符合实际环境演进；误删恢复是否方便
  - 占位链 `["dev"]` 在没有 `dev` 分支的工作区中的提示是否足够醒目
  - 保留仓库 `envs` 补链/删链后，切换工作区是否还有残留冲突

## v0.4.4 审核人配置与自动推断（2026-11-04）

- 来源：`/gitflow:merge` 实测时提出审核人是固定人员分配，希望配置在 `gitflow.json`；最初提出按分支划分负责人，随后澄清应按仓库划分。进一步提出 init 可能让用户一直不知道这个配置，建议从默认分支最近的 merge 人推断。
- 采纳：
  - `repos.<name>.reviewers` 为主配置，`mr.reviewers` 为全局回退；命令行 `--reviewer` 优先；`--no-reviewer` 强制置空
  - 仓库级 `[]` 表示显式不指定，不回退全局
  - `/gitflow:merge` 未配置审核人时不弹确认、不阻断；glab 因审核人失败才停摆
  - `/gitflow:init` 对字段缺失的仓库，读取默认环境分支最近 10 条 merge 提交，按邮箱计数取第一名写入；不排除自己或 bot；次数相同取最近一次；不覆盖已有值；不弹确认
  - 用户名优先取邮箱 `@` 前部分（去 `+tag`、转小写），不合法时退回作者名；仍不合法则留空
  - 新增 `--no-infer-reviewers`；推断失败不阻断 init，结果统一在最终摘要告知
- 决策：
  - 按仓库而不是按分支/环境：用户澄清负责人按仓库划分，避免多一层维度
  - 只取第一名而不是全部候选：用户明确要求，减少配置噪音；错误可由用户修正
  - 不排除 self/bot：用户明确要求，保持规则简单可预测
  - 写错可接受：目标首先是让用户发现配置入口并减少手工时间，不追求推断绝对准确
  - 未配置审核人时不弹确认：避免额外交互，MR 仍可依赖 CODEOWNERS
- 待实测：
  - 最近 10 条 merge 的第一名在真实仓库中的准确率与稳定性
  - 邮箱 local part 与 GitLab 用户名不一致时的回退效果
  - fast-forward/squash 仓库无 merge 提交时的摘要提示是否清晰
  - glab `--reviewer` 的实际传参形式（重复 vs 逗号分隔）与无权限/不存在用户的报错
  - 多个仓库复用同一审核人、单仓库多审核人的配置体验

## v0.4.3 sync 冲突的受限解决（2026-11-04）

- 来源：用户提出 `/gitflow:sync` 合并冲突时可以先让 AI 尝试解决，冲突过多或无法处理时再停摆；确认选择“解决后展示摘要，确认再提交并推送”。
- 采纳：
  - core 新增 §5.5：仅当用户在冲突现场明确选择后，AI 才在限额内尝试解决
  - 限额：≤5 文件 / ≤10 冲突块 / ≤300 冲突行；仅普通文本源码；锁文件、生成物、二进制、敏感文件、子模块、增删/改删冲突不尝试
  - 读取 base/ours/theirs 与两侧提交意图合并，禁止整段 ours/theirs
  - 解决后展示逐文件摘要与风险，确认才 `git add` + `git commit --no-edit`
  - sync 第 8 步补充领先上游检测，修复“合并完成但推送失败/手动解决后重跑不推送”
- 决策：
  - 不做无条件自动解决：跨版本冲突可能涉及业务语义，且 v0.4 没有类型检查/单测兜底
  - 确认环节保留在提交前，而不是推送前：让用户在进入历史前看到解决摘要
  - 冲突范围判断放在 core，命令文档只引用，避免规则漂移
- 待实测：
  - 限额（5 文件 / 10 块 / 300 行）在真实跨版本冲突中的覆盖率与噪音
  - AI 对同一函数两侧互斥语义的判断是否稳定，停摆提示是否清晰
  - 解决后 `git diff HEAD --check` 在未 `git add` 状态下对未合并索引的表现
  - 重跑 sync 的领先上游检测在无上游、上游被其他机器推进时的表现

## v0.4.2 跨仓库任务的分支准备（2026-11-04）

- 来源：pro-pcb 实测 `/gitflow:start` 时提出——一开始不确定其他仓库是否也要改；若开发中 AI 自己分析出本次任务还需修改其他仓库，是否应提示先建分支。用户澄清：只针对 AI 为本次任务所做的改动，不检测、也不自动操作与任务无关的手工改动。
- 采纳：
  - core 新增 §2.5.1：AI 判断本次任务涉及其他仓库时，在修改文件前用 `/gitflow:start <单号> --repo <仓库名> --branch <当前任务分支名>` 创建并切换同名对齐分支
  - §2.5 遗漏检测明确为只读兜底：不判断改动来源、不自动建分支/切换/stash
  - commit / sync / merge 修正“仓库不可用”描述；start 文档与输出增加跨仓库提示
- 决策：
  - 触发依据是任务内容而非 `git status`：工作区状态无法区分 AI 改动、其他任务与用户手工修改
  - 分支准备在修改文件前完成，避免在兄弟仓库的环境分支上直接改代码
  - 不做实时 hook：会话内由 AI 主动执行规则即可，hook 需要维护任务状态且噪音高
- 待实测：
  - 开发中 `/gitflow:start --repo <name> --branch <当前分支>` 在兄弟仓库创建并切换的体验
  - 兄弟仓库有无关手工改动导致无法切换时，停摆提示是否清晰
  - 长时间开发后 core 规则是否仍在上下文；提交时 §2.5 兜底是否足够

## v0.4.1 分支过滤与免确认（2026-11-03）

- 来源：pro-ui 环境实测。`/gitflow:init` 的 `git ls-remote --heads` 返回几十条分支，包含大量人名；每次运行还会要求确认是否写入 `gitflow.json`。
- 采纳：
  - 只请求 `<仓库键>/*` 前缀，并只保留版本号（`0.1`、`3.2`）或常见环境名（`dev` 等）的 token
  - 候选分支要求 tip 提交在最近 365 天内；只对名称过滤后的少量候选批量 fetch 读取时间
  - 展示草稿与摘要后直接写入/更新，不再二次确认；`--dry-run` 保留预览
  - 裸 `<env>` 不再作为候选；已有映射指向裸分支且没有对应的 `<仓库名>/<环境>` 时按未解析处理
- 决策：
  - 前缀过滤放在 `git ls-remote` 的 ref pattern 上，减少网络与输出噪音，而不是拉全量后本地过滤
  - 时间过滤只影响候选发现，不自动删除已有映射，避免误删“老但仍在用”的环境
  - 链级漂移（新增/疑似移除）仍需确认；只取消最终写盘确认，保留对内容变更的人工判断
- 待实测：
  - GitLab 对 `refs/heads/<repo>/*` 的 ls-remote pattern 支持
  - 候选分支批量 fetch 在部分克隆/大仓库下的耗时
  - 人名恰好形如版本号或环境名时（如某人叫 `dev`）是否仍会误入
  - 裸分支映射改为未解析后的停摆提示是否清晰

## v0.4.0 环境链自动探测（2026-11-03）

## v0.2.0 优化（2026-11-03）

- 来源：[project-docs/plans/gitflow-improvements.md](../../project-docs/plans/gitflow-improvements.md)（基于 v0.1.0 的多仓库环境使用反馈）
- 采纳并落地：
  - P0-1 多仓库协同三步：遗漏检测（默认只读提醒）、`--repo <name>` 显式操作兄弟仓库、`/git-flow-start --repos` 创建对齐分支
  - P0-2 `/git-flow-init`：扫描仓库、探测远端环境分支、草稿确认后落盘
  - P1 全部校准项：glab 内网登录指引、多行描述临时文件、glab 参数 `--help` 校准提示、手动入口 URL 推导与编码、pro-api 非同构示例、merge 先 fetch 后比较、预检注明快照
  - P2-2 sync 方向措辞、P2-3 停摆条件去重、P2-4 `commit.checks` 预留
- 决策：
  - 遗漏检测是“停摆提醒”而非硬拦截：用户确认后可继续，避免与当前任务无关的改动反复阻塞
  - 兄弟仓库对齐分支用 `git branch --no-track` 创建但不切换，避免未经确认改变其他仓库工作区
  - 配置 `path` 改为相对配置文件基准目录解析，配置版本升到 `2`；v1 配置明确停摆并提示重新生成
  - init 对无法自动匹配的环境分支（如 `pro-api/0.3`）一律停摆询问，允许多个环境映射到同一分支
  - merge 的 fetch 提前到推送状态校验之前，预检报告注明快照 hash，不把“无冲突”包装成服务端保证
  - glab 描述优先用临时文件 + `--description-file`，实际参数以 `--help` 为准；不支持时退回 `--description "$(cat ...)"`
  - 暂缓：`/git-flow-promote`（等实际遇到环境提升需求）、`commit.checks` 实际执行、已合并分支清理（GitLab 自动删除已覆盖大半）
- 复核反馈（2026-11-03，提交前自审）：
  - P1 修复：`--repo` 模式下 format-keeper / mojibake-fixer / commit-draft 默认按会话当前目录执行，会作用到错误仓库；core 新增 §2.6 统一上下文规则，commit 的格式化、乱码检查、提交信息生成均改为显式继承 `<root>`
  - P2 修复：`/git-flow-start --repos` 不再因兄弟仓库工作区不干净而停摆——`git branch` 只写引用，改为提醒后继续
  - P2 采纳：遗漏检测区分「正在同名任务分支」与「仅存在同名分支（未检出）」
  - P3 修正：改进建议文档 `git diff -U` 笔误改回 `git diff`
- 待实测：
  - 工作区多仓库遗漏检测的提醒频率与噪音（当前任务无关改动是否过多）
  - `git branch --no-track` 在 Windows 中文/带空格路径下的表现
  - 内网 GitLab 的 glab 认证与 `--description-file` 实际参数名
  - `git ls-remote` 在仓库多、网络慢时的 init 耗时
  - 工作区根目录配置与仓库内配置同时存在时的匹配行为
  - merge 预检快照措辞是否足以避免过度信任“无冲突”

## 初始创建（2026-11-02）

- 需求来源：[project-docs/plans/gitflow.md](../../project-docs/plans/gitflow.md)；经评估后用户确认：环境分支采用链式同步、未指定环境默认链式顶端（通常 `dev`）、异常停摆询问用户、指令名改为 `git-flow-*`、提交前走“add → 格式化 → 乱码修复 → add → commit-draft → commit → push”。
- 决策：
  - 采用聚合套件 + `git-flow-core` 共享技能，避免四个命令复制规则。
  - 配置以仓库 `.claude/git-flow.json` 为主，全局默认放 `settings.json#gitFlow`（由 `_base.json` 维护）；不直接依赖 `~/.claude/settings.json` 的手工改动。
  - v0.1 只做“任务分支 → 所属环境”的 MR，环境链提升留待 `/git-flow-promote`；避免一次实现过多未验证逻辑。
  - MR 自动创建依赖 `glab`；不可用时停摆并给出手动入口，不用 `git push -o merge_request.create` 兜底（分支已推送时 push 是 no-op）。
  - 冲突只预检不解决；破坏性操作一律不自动执行。
- 待实测确认项：
  - 实际 ONES 粘贴格式（多行、链接、标题）的解析准确率
  - `glab mr create/list` 的参数名随版本变化，需在真实环境核对 `--help`
  - Windows 下 `merge-tree` 输出解析、长路径、中文路径
  - 多仓库工作区配置匹配（`path` 解析、嵌套仓库）
  - 提交流水线在 Prettier/ESLint/Biome 项目中的实际表现，以及 `skipped` 是否可接受
  - 链式环境提升的真实操作顺序与 MR 目标分支
