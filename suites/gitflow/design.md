# design.md

## gitflow 设计

### 背景

团队使用长期环境分支（`dev` / `4.1` / `3.2` / ...），任务从环境拉出、通过 MR 合回。重复劳动集中在：生成环境分支映射、从 ONES 工单建分支、同步环境、提交前格式化/查乱码/写 message、创建 MR。这些步骤规则明确，适合 AI 执行；但跨版本冲突、环境判断、权限异常需要业务判断，必须留给人。

本地工作环境进一步放大了这个问题：专业版编辑器由多个平级仓库协作（`pro-ui`、`pro-pcb`、`pro-sch`、`pro-api` 等），一次任务经常同时修改多个仓库，而 git 提交按仓库隔离。AI 一次改两个仓库后，只提交当前仓库会静默遗漏兄弟仓库。

设计哲学：**AI 只负责正常流程的重复劳动，异常停摆或交给人。** 不追求“全自动”，追求“可预测、可中断、可恢复”。

### 关键设计决策

#### 1. 聚合套件 + 共享核心技能

六个命令共享配置读取、操作仓库解析、环境链、前置检查、多仓库检测、ONES 解析与安全边界。把这些放进 `gitflow-core` 技能，命令只描述自身差异：

- 规则单一来源，改一处所有命令同时生效
- 命令文档更短，避免复制粘贴导致规则漂移
- `/gitflow:promote` 也复用同一套分支命名、环境链与受限冲突规则

#### 2. 命令使用 `gitflow:` 命名空间

`git-start` / `git-commit` 这类名字与 Git 原生命令高度相似，容易误解为 Git 子命令；单层 `git-flow-*` 虽能隔离语义，但前缀冗长、命令文件平铺。v0.3 起统一放入 `commands/gitflow/` 目录，调用为 `/gitflow:init`、`/gitflow:start` 等：

- 斜杠命令与 Git 命令在语义上清晰隔离
- 命名空间与套件同名，`~/.claude/commands/gitflow/` 下即可看到全部子命令
- 结构参考 OpenSpec 套件的 `/opsx:*`

#### 3. 链式环境模型

```text
3.1 → 3.2 → 4.1 → dev
```

- 任务分支只合回**所属环境**，不直接从任务分支向多个环境开 MR
- 环境之间按链式顺序逐级提升，避免同一改动在多条路径重复合并、产生不同步
- 未指定环境时默认链式顶端（通常 `dev`）：用户确认“没有指定就用最新”，减少每次输入
- 任务 → 所属环境由 `/gitflow:merge` 完成；环境 → 更高环境由 `/gitflow:promote` 完成：从目标环境新建任务分支、cherry-pick 原提交，再走 merge 流程（v0.5.0，见决策 25）

#### 4. 唯一全局配置

**仓库-环境分支映射在本机多个克隆之间是同一套事实**。v0.4 起只保留一份配置 `~/.claude/gitflow.json`：

- 不创建项目/工作区 `.claude/gitflow.json`，不读取 `settings.json#gitflow`，不支持 `GITFLOW_CONFIG` 覆盖
- 原因：本机多个 `pro-ui` / `pro-pcb` 克隆需要共享同一套映射；多来源优先级会增加“改了不生效”的排查成本
- `repos.*.path` 相对工作区目录解析，缺省为仓库键名，同一份配置适配多个克隆
- 配置可以包含多个本地工作区的仓库；当前工作区缺失的条目在检测时跳过
- `/gitflow:init` 默认只更新当前仓库条目，`--all` 扫描父目录下全部兄弟仓库；未扫描条目原样保留
- 配置是个人文件，不提交 Git；需要团队共享时，各成员在本地生成相同映射

`claude-lab deploy gitflow` 只部署命令、技能与文档，不创建或更新配置文件。

#### 5. 提交按固定流水线

用户明确要求：`git add -A` → mojibake-fixer → format-keeper → 再次 `git add -A` → commit-draft → commit → push。

- 先 add 让乱码检查与格式化工具都看到完整变更范围
- **先修乱码、后格式化**（v0.4.6）：乱码修复会改写文本内容，可能改变行长与字符宽度，若之后再修乱码会破坏刚生成的格式；把格式化放在最后，可重新归一前序步骤引入的偏差
- 格式化后再 add，保证乱码修复与格式化结果都进入提交
- commit-draft 生成 Conventional Commits 信息，单号从分支名与会话 ONES 内容提取
- 默认 push；`--no-push` 可只提交
- 当前版本不跑 TS 类型检查与单元测试；配置 `commit.checks` 预留数组位，未来按项目启用时只改配置

#### 6. 格式化独立成 `format-keeper`

格式化是可独立运行、也可内嵌的步骤，做成技能而非命令：

- 需要按项目检测工具、按扩展名分组、区分 `skipped` / `failed`
- `/gitflow:commit` 只引用其规则与状态，不复制实现
- 同时支持 `/format-keeper` 手动执行

#### 7. 上游跟踪修复

从远端环境分支创建任务分支时使用 `git checkout --no-track -b`。若不加 `--no-track`，任务分支会跟踪环境分支，`git push` 可能被 `push.default=simple` 拒绝，或误推向环境分支。首次 push 由 `/gitflow:commit` 使用 `git push -u origin HEAD` 建立正确上游。

#### 8. 冲突默认停摆，sync 可选受限解决

- `/gitflow:sync`：真实 merge；冲突时先列出文件与范围，由用户选择是否让 AI 尝试解决（v0.4.3，见决策 20）
- `/gitflow:promote`：真实 cherry-pick；冲突在 core §5.5 同一限额内**自动**解决并继续（v0.5.0，见决策 25），超出限额即停摆
- `/gitflow:merge`：`git merge-tree --write-tree --name-only` 只读模拟，不碰工作区；有冲突只报告文件，不创建 MR
- 不提供 ours/theirs 自动选择：跨版本冲突方向往往需要业务判断

#### 9. 停摆优先

以下情况一律停摆并给出选项，不猜测、不重试、不绕过：

- 工作区不干净、进行中的 merge/rebase、detached HEAD
- 配置缺失/非法、环境不确定、环境分支不存在
- 工单解析失败、类型无法确定、同名分支已存在
- 冲突超出受限解决范围或用户未选择 AI 解决、push 被拒绝、glab 不可用、审核人配置非法或 glab 因审核人失败、状态与预期不符

停摆报告必须说明：发生了什么、哪些动作未执行、可选方案。

例外：`/gitflow:init` 的配置决策（链级增删、未解析映射、`active`/`default_env` 修正）按推荐方案自动处理并在摘要告知，见决策 22。

#### 10. 多仓库协同分三层，全部显式触发

多仓库是常态而非异常，但“自动跨仓库操作”风险高，因此拆成三层：

1. **改动检测（默认，不打断）**：commit / sync / merge 开头扫描其他配置仓库，以当前分支名判断任务归属。同名分支且有未提交改动 = 同一任务：`/gitflow:commit` 自动按同一流水线提交（v0.4.7，见决策 23），sync / merge 只提示不处理；不同分支的改动一律忽略。不再弹窗询问。
2. **`--repo <name>`**：命令显式操作配置中的某个兄弟仓库，内部用 `git -C`，会话不切目录。不自动切换、不自动选择，也不会触发其他同名分支仓库的自动提交（显式范围优先）。
3. **`--repos <a,b,c|all>`**：`/gitflow:start` 为兄弟仓库创建同名对齐任务分支（同环境、同单号），用 `git branch --no-track` **只创建、不切换**；`/gitflow:promote` 依次提升指定仓库，兄弟仓库在系统临时目录的独立 worktree 中处理，同样不切换主工作区。工作区不干净只提醒，不阻断。

多仓库改动靠工单号关联，不引入额外元数据。

#### 11. `/gitflow:init` 创建与增量更新

5 个常用仓库 × 3 个环境 = 15 条映射，手写易错。初始化命令：

- 默认只扫描当前仓库；`--all` 扫描当前仓库根目录父级下的直接子仓库
- 只写 `~/.claude/gitflow.json`：文件不存在则创建，已存在则**增量更新**本次涉及的仓库条目
- 未传 `--envs` 时：首次从远端分支自动探测环境链（只读取 `<仓库键>/*` 中 `X.Y` 版本号/环境名且最近 365 天有提交的分支）；已有 `chain` 则沿用并自动应用新增/疑似移除的环境
- 单仓库 init 不主动删除链级环境；`--all` 才基于全部目标仓库的映射证据移除；已有配置时新增环境不会自动加入 `active`
- 每个仓库一次 `git ls-remote --heads <remote> "refs/heads/<key>/*"`；现有映射仍存在时优先沿用；否则按 `<仓库键>/<环境>` 名称匹配（存在即可，不要求活跃）
- 未解析映射不询问：目标环境只有唯一候选时自动映射；0 个或多于 1 个候选时留空并在摘要列出，不猜测
- 保留未扫描的仓库条目与未知手工字段；失效的环境键移除并在摘要中列出
- 展示草稿与变更摘要后直接落盘，不再等待写盘确认；支持 `--dry-run` 预览

#### 12. 配置路径以“工作区目录”解析

v0.1 的 `path` 相对当前仓库根目录解析，多仓库配置在不同仓库内执行会得到不同结果。v0.4 只保留全局配置后：

- base = 工作区目录（当前仓库根目录的上一级）；不能使用配置文件所在目录，否则 `path: "pro-ui"` 会在 `~/.claude` 下解析
- `path` 缺省为仓库键名（`<workspace>/<repo-name>`）；标准兄弟布局可省略
- 配置版本保持 `2`；旧版本明确停摆并提示用 `/gitflow:init` 重新生成
- 同一份全局配置在任意仓库内执行命令都能解析出相同的工作区路径，不随当前目录变化

#### 13. merge 先 fetch 再比较，预检注明快照

- `fetch` 提前到推送状态校验之前，避免 remote-tracking 快照过期导致“本地与上游一致”的误报
- `merge-tree` 预检基于 fetch 时点的目标分支，报告注明 `<remote>/<env> @ <hash>`，并提示服务端合并时目标分支可能已前进

#### 14. 文档收敛与 glab 适配

- 各命令的“停摆条件”只列命令特有项，通用项引用 core §2/§5，遵守“core 单一规则来源”
- `/gitflow:sync` 的方向统一表述为“环境分支 → 任务分支”，避免读反
- glab：内网 GitLab 需 `--hostname` / `GITLAB_HOST`；描述优先用临时文件 + `--description-file`（以 `--help` 为准），规避 Windows 多行引号转义；手动入口的 Web URL 由 `git remote get-url` 按规则推导并对分支名 URL 编码

#### 15. 内嵌技能继承操作仓库上下文

`format-keeper`、`mojibake-fixer`、`commit-draft` 默认以“当前目录所在仓库”为工作对象；`--repo` 模式下会话当前目录可能不是操作仓库。core §2.6 规定调用时显式继承 `<root>`：

- git 命令一律 `git -C <root>`；`npm run` / `lc-build` 在 `<root>` 下执行
- mojibake-fixer 显式传入 `<root>` 下的变更文件绝对路径
- commit-draft 的信息收集命令替换为 `git -C <root> ...`
- 不依赖上一条命令的 `cd` 状态

#### 16. 全面改名 `gitflow`（v0.3.0 破坏性变更）

套件、技能、命令命名空间、配置文件名与全局键统一为 `gitflow`：

- 套件目录 `suites/gitflow/`，共享技能 `gitflow-core`
- 命令落入 `commands/gitflow/`，调用 `/gitflow:init` 等；manifest 映射 `commands/gitflow/*.md` → `~/.claude/commands/gitflow/`
- 配置统一为 `~/.claude/gitflow.json`（v0.4.0 进一步收敛为唯一全局文件，见决策 17）
- 旧名 `/git-flow-*`、`.claude/git-flow.json`、`gitFlow` 不再识别；v0.3 尚未部署，无迁移成本

改名动机：套件名、命令前缀、技能名、配置名此前各用一套写法（`git-flow` / `git-flow-*` / `gitFlow`），使用者需要在多种形态间换算。统一为单个词 `gitflow` 后，目录、命令命名空间、技能名与配置键一一对应，也避免了命令文件平铺在 `commands/` 根目录。

#### 17. 配置来源收敛为唯一全局文件（v0.4.0）

用户实测后澄清：只希望维护一份 `~/.claude/gitflow.json`。在 `pro-ui` 内运行 `/gitflow:init` 应只新增/更新 pro-ui 条目；`--all` 才扫描父目录下全部仓库。项目/工作区目录不应出现配置，也不存在优先级；`claude-lab deploy gitflow` 不管理配置。

v0.4.0 的选择：

- 唯一路径 `~/.claude/gitflow.json`；删除项目/工作区配置、`settings.json#gitflow` 默认值与 `GITFLOW_CONFIG` 覆盖
- `/gitflow:init` 默认单仓库、`--all` 扫描兄弟仓库；已存在时增量更新，保留未扫描条目与手工字段
- base 固定为工作区目录，`path` 缺省仓库键名；配置可以跨多个本地工作区复用
- 配置可包含当前工作区没有的仓库：遗漏检测与 `--repos all` 跳过缺失条目；显式 `--repo` / `--repos` 指定缺失仓库仍停摆
- 代价：不能再用项目配置做单项目覆盖；团队共享不再自动，需各成员本地生成；克隆目录名不同会新增独立条目
- `claude-lab deploy gitflow` 只部署命令、技能与文档，不创建或更新 `~/.claude/gitflow.json`

#### 18. 环境链自动探测与漂移（v0.4.0，v0.4.1 增强，v0.4.5 改为自动应用）

固定示例链（曾写作 `3.1,3.2,4.1,4.2,dev`）会随环境演进过时——新增 `5.1`、下线 `4.2` 后文档与实际不符。v0.4.0 让 `/gitflow:init` 从远端分支推断，v0.4.1 增加前缀与活跃时间过滤，v0.4.5 起自动应用漂移：

- 未传 `--envs` 时：首次无 `chain` → 只从 `git ls-remote --heads <remote> "refs/heads/<key>/*"` 拉取前缀分支，再过滤 `X.Y` 版本号/环境名与最近 365 天活跃窗口；已有 `chain` → 沿用并自动应用漂移
- 过滤掉人名、任务分支、裸 `<env>`、`release/4.1` 等带额外层级的分支，以及多段数字版本号（`3.2.0918`、`5.1.2`）；候选版本号必须是 `^\d+\.\d+$` 或常见环境名（`dev`、`test` 等）
- 活跃时间只影响候选发现：tip 提交不在本地时只批量 fetch 通过名称过滤的候选分支，读取 committer date；读取失败的候选被排除；已有映射只按分支是否存在保留，不因超过一年未提交自动删除
- 排序：版本号按数字升序；非版本环境按内置常见顺序；`dev` 默认置顶
- 漂移：新增环境按排序规则自动插入；疑似移除需满足「无任何目标仓库有效映射 + 至少一个仓库曾配置且分支消失 + 不在锚点仓库候选集」，自动移除
- 单仓库 init 不主动删除链级环境，`--all` 才基于全部目标仓库自动移除；证据不足一律保留
- 已有配置时新增环境不自动加入 `active`（首次初始化没有既有 `active`，仍等于探测出的 `chain`）；移除环境从 `active` 剔除，`default_env` 回退到 `active` 最后一项
- 显式 `--envs` 完全跳过探测与自动增删；token 含多段数字版本号时直接报错；探测只覆盖 `<仓库键>/<X.Y 版本号或环境名>` 且一年内活跃的分支，裸分支、`release/4.1`、`v4.1` 等不会被自动发现，映射需对应前缀分支或显式指定
- 链级增删不再人工确认：直接写入，摘要标明新增、移除与排除的非法版本号；用户不满意时编辑配置或下次用 `--envs` 覆盖

#### 19. 跨仓库任务的分支准备（v0.4.2）

用户澄清：这里说的“其他仓库有变更”指 AI 在实现过程中**自己分析出本次任务还需要改其他仓库**；不是扫描用户手工改动的代码并替它自动建分支。工作区改动本身无法区分来源（当前任务 / 其他任务 / 用户手工），因此不能由 `git status` 反推任务归属。

v0.4.2 的选择：

- core 新增 §2.5.1：AI 判断本次任务涉及其他仓库时，在修改文件前用 `/gitflow:start <单号> --repo <仓库名> --branch <当前任务分支名>` 创建并切换同名对齐分支
- 只对本次任务确认要改的仓库执行；切换会覆盖或冲突未提交改动时停摆询问，不 stash、不覆盖
- §2.5 改动检测保留为提交/同步/合并时的兜底：以分支名对齐判断“是否同一任务”，不依据改动内容推断归属；不自动建分支/切换/stash。v0.4.7 起 commit 对已检出同名分支的仓库自动提交，见决策 23
- 不做实时 hook：AI 在会话中主动执行规则即可；hook 需要维护任务状态，且无法判断改动是否属于本任务，噪音高

#### 20. 受限冲突解决与同步重跑（v0.4.3）

用户提出：`/gitflow:sync` 合并冲突时可以先让 AI 尝试解决，冲突过多或无法处理时再停摆。采纳为“受限 + 确认”，而不是无条件自动：

- 触发必须由用户在冲突现场明确选择；默认仍是停摆
- 范围硬限制：≤5 文件、≤10 冲突块、≤300 冲突行；仅普通文本源码；锁文件、生成物、二进制、敏感文件、子模块、`DD/AU/UA/DU/UD` 冲突不尝试
- 解决依据是 base/ours/theirs 三个版本与两侧相关提交，按意图合并；禁止整段 ours/theirs
- 解决后先展示逐文件摘要与风险，用户确认后才 `git add`（仅冲突文件）+ `git commit --no-edit`
- 无法确定业务取舍、校验失败或用户不确认 → 停摆，保留编辑，不自动 abort
- 同时修复重跑缺口：merge 已完成但推送失败、或手动解决冲突后重跑 sync 时，第 8 步在“落后 0”后继续比较 `@{u}..HEAD`，有领先提交则跳到推送

不采用无条件自动解决的依据：跨版本冲突可能涉及业务语义，且 v0.4 没有类型检查/单测兜底；确认环节放在提交前，让用户在进入历史前看到解决摘要。

#### 21. 审核人按仓库配置与 init 自动推断（v0.4.4）

用户提出审核人是固定人员分配，希望配置在 `~/.claude/gitflow.json`；同时担心 `/gitflow:init` 不初始化审核人，用户可能一直不知道有这个配置。采纳为“按仓库配置 + init 静默推断”：

- 审核人按**仓库**划分（不是按分支/环境）：`repos.<name>.reviewers` 是主配置，`mr.reviewers` 作为全局回退；同一人可负责多个仓库，一个仓库可多人
- `/gitflow:merge` 解析顺序：命令行 `--reviewer` → `repos.<name>.reviewers` → `mr.reviewers` → 空；`--no-reviewer` 强制置空；仓库级 `[]` 表示显式不指定，不再回退
- 未配置审核人时不弹确认、不阻断 MR：创建不带审核人的 MR，结果注明配置路径；glab 因审核人失败时停摆并指出字段，不静默去掉审核人重试
- `/gitflow:init` 对字段缺失的仓库自动推断：读取默认环境分支（`default_env` 映射；缺失时取 `active` 中该仓库最高环境）最近 10 条 merge 提交，按作者邮箱计数，取第一名，不排除自己或 bot；次数相同取最近一次 merge
- 用户名优先取邮箱 `@` 前部分（去掉 `+tag`、转小写），不合法时退回作者名；仍不合法则留空
- 只写缺失字段，绝不覆盖已有值（包括 `[]`）；不弹确认，推断依据与结果统一放在最终摘要；`--no-infer-reviewers` 可跳过
- 推断错误可接受：目标是让用户发现配置入口并减少手工时间，用户可随时修正

不采用“按分支/环境配置审核人”：用户澄清负责人按仓库划分，多一层维度会增加配置与解析复杂度。也不采用“候选全部写入”：用户明确只取第一名。

#### 22. init 非交互与严格版本号（v0.4.5）

用户实测后提出：`/gitflow:init` 遇到未解析映射、环境链里是否保留 `3.2.0918` 这类条目时不应弹窗询问；AI 按推荐方案直接创建/更新 `~/.claude/gitflow.json`，完成后统一告知，用户发现问题再调整。核心是减少前置交流：

- **init 全程不询问**：链级增删、未解析映射、`active`/`default_env` 修正都按确定性规则自动处理，结果写入最终摘要
- **未解析映射**：按环境类型收窄候选池后，恰好 1 个候选才自动映射；0 个或多于 1 个候选时留空，摘要列出候选，不猜测。留空的环境不写入 `envs`，后续命令用到时按 core §1.3 停摆
- **版本号收紧为 `^\d+\.\d+$`**：只保留数字.数字结构；`dev`、`main` 等环境名照常识别；多段数字（`3.2.0918`、`5.1.2`）不是版本号，探测时排除，已有 `chain` 中的这类条目自动剔除，显式 `--envs` 传入则报错
- **链级漂移自动应用**：新增环境按排序插入，疑似移除按证据自动删除；单仓库 init 仍不主动删除链级环境
- **保留仓库的过期 `envs` 键**：未传 `--envs` 时补入 `chain`；显式 `--envs` 时删除并摘要列出；多段数字键直接删除。不再停摆
- **占位链**：没有任何候选且未传 `--default-env` 时写入 `["dev"]` 并在摘要提示手工调整，而不是停摆
- **只有真正错误才停摆**：不在 Git 仓库、配置损坏、远端不可达、显式参数非法、目录名重复、草稿校验失败、写入失败

不采用“重复询问直到用户确认”的原因：用户明确希望 init 一次跑完；推荐方案错误时编辑 JSON 的成本低于逐项交互，且配置是个人文件、可随时重跑。

#### 23. 多仓库改动按同名分支自动提交（v0.4.7）

用户实测：在 pro-pcb 提交时，其他仓库里自己改的、与本次任务无关的改动会触发弹窗询问，造成干扰。用户明确规则：其他仓库有变动不弹窗、默认不提交；只有其他仓库当前分支与当前仓库**同名**时才提交（说明是跨仓库处理同一任务）；否则一律不处理。

- 任务归属只看**当前检出分支名**是否完全相同；不看改动内容，也不看是否仅存在同名分支引用
- `/gitflow:commit` 缺省模式：操作仓库完成后，对「同名分支 + 有未提交改动」的仓库逐个执行同一流水线（敏感文件检查 → `git add -A` → 乱码 → 格式化 → `git add -A` → 提交信息 → commit → push）；`--message` / `--no-push` 同样作用于这些仓库
- 显式 `--repo <name>` 只处理该仓库，不触发兄弟仓库自动提交；不同分支的改动一律忽略，只在摘要列出仓库与分支
- 同名仓库若 detached、处于 merge/rebase 等操作中、指向保护分支或命中未确认的敏感文件 → 跳过并记录原因，不询问、不阻断其他仓库
- `/gitflow:sync`、`/gitflow:merge`：检测只写入摘要，同任务未提交改动提示“未处理”，不停摆
- 风险：同一分支上若混入无关改动，会被视为同一任务一并提交；可通过 `--repo` 只提交指定仓库，或先清理工作区规避

不采用“继续弹窗让用户选择”的原因：用户已明确其他分支的改动通常属于其他任务，弹窗只会打断主流程；分支名相同是团队既有的任务对齐约定（`/gitflow:start --repos` 也用它）。

#### 24. MR 模板的可读性细节（v0.4.8）

用户实测 `/gitflow:merge` 生成的 MR 模板后提出三点：

- **关联工单要可点击**：有链接和标题时写成 Markdown 链接 `[PRO-159115 【标题】](链接)`，不再把标题和链接分成两行纯文本
- **合并链路要分行**：GitLab Markdown 会把连续行渲染成同一段，`源分支` / `目标分支` / `本次合并为` 必须各留一个空行，否则提交后挤成一行
- **去掉 `## 审核人` 标题**：`/assign_reviewer` 是 GitLab quick action，提交后会被执行并移除，只留下空标题；审核人指令直接放在描述末尾，无审核人时整行省略

实现落在 `/gitflow:merge` 步骤 12 的默认模板与填充规则；仓库自带模板仍按占位符填充，`{{reviewers}}` 为空时删除整条指令行。

#### 25. 环境提升走“新建任务分支 + cherry-pick”（v0.5.0）

用户实测 `/gitflow:merge` 后提出：任务分支已合入 `pro-pcb/4.1`，希望继续提升到 `dev`。期望流程是“按 `/gitflow:start` 从目标环境建分支 → 逐一 cherry-pick 本次合并的提交（冲突尽量解决，解决不了停摆）→ 再走 `/gitflow:merge`”，并认为不同版本各建分支互不干扰、也更好解决冲突。

v0.5.0 采纳该流程，`/gitflow:promote` 不直接创建“环境分支 → 环境分支”的 MR：

- **新建独立提升分支**：按 `branch_pattern` 把 `{version}` 换成目标环境，从 `<remote>/<目标环境分支>` 创建并 `--no-track`。源任务分支和源/目标环境分支都不被改写；提升冲突只影响新分支，已合入的源环境保持稳定
- **提交识别**：优先在源环境最近 200 条 merge 提交中找父提交包含源分支 tip 的合并提交，取 `^1..<source-tip>` 范围并排除 merge 提交；squash 合并时在最近 50 条提交中按工单号找唯一提交；快进/rebase/标题不含单号等无法识别时，要求 `--commits <base>..<head>` 或单个 `<sha>`，不猜测
- **过滤**：目标环境已包含的提交按祖先关系跳过；merge 路径再用 `git cherry` 跳过补丁等价提交；清单为空视为该仓库失败
- **冲突自动解决**：沿用 core §5.5 的限额与排除项，但 promote 不逐次询问——限额内解决后直接 `git add` + `git cherry-pick --continue`，记录摘要；超出限额、非冲突失败或空提交则停摆并保留现场，不 `--skip`、不 `--abort`
- **多仓库**：操作仓库始终处理；兄弟仓库必须显式 `--repos`（`all` 只展开存在源分支的仓库，能否提升由逐仓库识别判断），各自在临时 worktree 中完成建分支、cherry-pick、推送与 MR，结束后干净则移除 worktree；仓库之间失败隔离
- **MR 复用 merge 流程**：推送后按 `/gitflow:merge` 第 7-15 步创建 MR，`merge_type` 为“链式同步”（相邻）或“用户指定”（跳过中间环境）；`glab` 一律在对应仓库根目录执行

不采用“环境分支 → 环境分支”MR：源环境是保护分支，直接开 MR 会让提升与日常合入混在同一条历史线上，冲突解决也无法隔离到单个版本。也不采用“复用源任务分支直接改目标环境”：同一分支无法同时表达两个环境的基线，后续追溯与重试都会混乱。

代价与边界：merge/squash 之外的合并方式需要 `--commits`；源分支内部的 merge 提交不会被逐个重放；自动解决仍可能语义错误，依赖后续 review；临时 worktree 在失败时保留，需要用户手工清理（不使用 `--force`）。

### 与现有模块的关系

- `format-keeper`：提交流水线的格式化步骤
- `mojibake-fixer`：提交流水线的乱码检查步骤
- `commit-draft`：提交信息生成
- `ones-parser`：工单解析（优先使用）
- `gitflow-core`：本套件共享规则

### 已知限制（v0.5.0）

- `commit.checks` 仅预留，不执行
- 自动创建 MR 依赖 `glab`；不可用时只能给出手动入口
- 跨仓库写操作默认必须显式 `--repo`/`--repos`；唯一例外是 `/gitflow:commit` 缺省模式下自动提交检出同名任务分支的兄弟仓库，且仍不切换其他仓库工作区
- 改动检测会读取所有配置仓库的 `git status`；仓库多时有一定开销；不同分支的改动自动忽略，不再询问
- 同名分支自动提交假定“分支名相同 = 同一任务”；若同一分支混入无关改动，会被一并提交，需要用户自行保持分支干净或用 `--repo` 限定
- 兄弟仓库自动提交失败只跳过该仓库、不回滚，也不阻断主仓库；需要查看摘要后手动重跑
- 跨仓库分支准备依赖 core 规则在上下文中的持续存在；长时间开发或会话压缩后可能被遗忘，提交时的 §2.5 只读检测作为兜底
- 冲突解决为受限、需确认：超出 core §5.5 范围（锁文件/二进制/生成物/敏感文件/删除冲突/超过 5 文件 10 块 300 行）或 AI 无法确定业务取舍时仍停摆
- 受限冲突解决没有类型检查/单测兜底，只校验冲突标记与 `git diff --check`；语义正确性依赖用户确认与后续 review
- `/gitflow:promote` 的 cherry-pick 冲突在限额内自动解决、不逐次确认，语义错误只能在 MR review 时发现
- 提交识别只覆盖 merge 提交、唯一 squash 提交与显式 `--commits`；fast-forward、rebase、squash 标题不含工单号时需要手工提供范围
- 源任务分支内部的 merge 提交被排除，其冲突解决改动不会自动重放
- 提升分支命名必须与源分支不同；同名提升分支已存在（本地或远端）时直接失败，不复用、不覆盖、不删除
- 兄弟仓库使用临时 worktree，失败时保留现场供排查；不会自动 `worktree remove --force`，需要手工清理
- `/gitflow:promote` 不隐式提升同名分支的兄弟仓库，必须显式 `--repos` 或 `--repos all`
- `--commits` 单提交模式仅支持单仓库；多仓库提升时每仓库都需要能自动识别或分别执行
- 审核人推断基于 merge 提交人，可能不等于实际负责人（如发布经理、集成人）；GitLab 用户名由邮箱/作者名推导，也可能与实际账号不一致，需手工修正
- fast-forward/squash 工作流没有 merge 提交，无法自动推断审核人；只能手工配置或使用全局回退
- 审核人只在字段缺失时推断；人员分工变化或默认环境调整后不会自动更新，需删除字段重跑 init 或手工修改
- 未配置审核人的 MR 仍会创建，可能漏掉人工 review；依赖 CODEOWNERS 或用户后续补充
- Git 需 ≥ 2.38（`merge-tree --write-tree`）
- 唯一配置假设各本地工作区的仓库目录布局一致；目录名不同时，在该克隆运行 `/gitflow:init` 会新增独立条目
- 配置是个人文件，不随团队同步；团队共享需各成员本地生成相同映射
- 不再支持项目级覆盖；删除仓库或改目录名后，旧条目不会被自动清理，需手工删除
- `/gitflow:init --all` 只扫描当前工作区的直接子仓库，不递归嵌套仓库
- 环境链自动探测只识别 `<仓库键>/<X.Y 版本号或环境名>` 且最近 365 天有提交的分支；裸 `<env>`、`release/4.1`、`v4.1`、多段数字版本号（如 `3.2.0918`）等需显式 `--envs` 与手工映射
- 多段数字版本号被设计性排除：确实需要这种环境名时只能手工编辑配置，或改用 `X.Y`/环境名命名
- 活跃窗口固定 365 天；超过一年无提交的环境不会被自动发现，但已有映射仍会保留，手工映射也可指向前缀列表中的旧分支
- 前缀使用仓库目录名（键）；克隆目录名与远端仓库名不一致时探测不到对应的 `<仓库名>/*` 分支，需显式 `--envs` 与手工映射
- 首次探测需要为少量候选分支执行 `git fetch --no-tags` 读取 tip 提交时间；大仓库下会增加少量网络开销
- 单仓库 init 不删除链级环境；环境下线后需 `--all` 或显式 `--envs` 才能从 `chain` 移除
- 未解析映射只做“唯一候选自动映射”，多候选时留空；后续命令在该仓库使用该环境时会停摆，需手工补 `envs`
- 没有候选时写入占位链 `["dev"]`，可能不符合实际环境；需手工调整或下次显式 `--envs`
- 链级增删与保留仓库 `envs` 键的调整都是自动的；调整依据只看分支与映射证据，可能与实际业务下线计划不一致，需要用户复核摘要
- 已有配置时新增环境不自动加入 `active`，首次使用前需传 `--active` 或手工编辑
- 版本号排序假设数字版本顺序；非版本环境依赖内置常见名列表，未知命名可能排序不符合预期
- 已合并分支清理未自动化；依赖 GitLab `mr.remove_source_branch` 与合并后自动删除
