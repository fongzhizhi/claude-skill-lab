# design.md

## gitflow 设计

### 背景

团队使用长期环境分支（`dev` / `4.1` / `3.2` / ...），任务从环境拉出、通过 MR 合回。重复劳动集中在：生成环境分支映射、从 ONES 工单建分支、同步环境、提交前格式化/查乱码/写 message、创建 MR。这些步骤规则明确，适合 AI 执行；但跨版本冲突、环境判断、权限异常需要业务判断，必须留给人。

本地工作环境进一步放大了这个问题：专业版编辑器由多个平级仓库协作（`pro-ui`、`pro-pcb`、`pro-sch`、`pro-api` 等），一次任务经常同时修改多个仓库，而 git 提交按仓库隔离。AI 一次改两个仓库后，只提交当前仓库会静默遗漏兄弟仓库。

设计哲学：**AI 只负责正常流程的重复劳动，异常停摆或交给人。** 不追求“全自动”，追求“可预测、可中断、可恢复”。

### 关键设计决策

#### 1. 聚合套件 + 共享核心技能

五个命令共享配置读取、操作仓库解析、环境链、前置检查、多仓库检测、ONES 解析与安全边界。把这些放进 `gitflow-core` 技能，命令只描述自身差异：

- 规则单一来源，改一处所有命令同时生效
- 命令文档更短，避免复制粘贴导致规则漂移
- `gitflow-core` 也可被后续命令（如 `/gitflow:promote`）复用

#### 2. 命令使用 `gitflow:` 命名空间

`git-start` / `git-commit` 这类名字与 Git 原生命令高度相似，容易误解为 Git 子命令；单层 `git-flow-*` 虽能隔离语义，但前缀冗长、命令文件平铺。v0.3 起统一放入 `commands/gitflow/` 目录，调用为 `/gitflow:init`、`/gitflow:start` 等：

- 斜杠命令与 Git 命令在语义上清晰隔离
- 命名空间与套件同名，`~/.claude/commands/gitflow/` 下即可看到全部子命令
- 结构参考 OpenSpec 套件的 `/opsx:*`

#### 3. 链式环境模型

```text
3.1 → 3.2 → 4.1 → dev
```

- 任务分支只合回**所属环境**，不直接从任务分支向多个环境开 MR
- 环境之间按链式顺序逐级提升，避免同一改动在多条路径重复合并、产生不同步
- 未指定环境时默认链式顶端（通常 `dev`）：用户确认“没有指定就用最新”，减少每次输入
- v0.4 先实现任务 → 所属环境的 MR；环境提升留给后续 `/gitflow:promote`

#### 4. 唯一全局配置

**仓库-环境分支映射在本机多个克隆之间是同一套事实**。v0.4 起只保留一份配置 `~/.claude/gitflow.json`：

- 不创建项目/工作区 `.claude/gitflow.json`，不读取 `settings.json#gitflow`，不支持 `GITFLOW_CONFIG` 覆盖
- 原因：本机多个 `pro-ui` / `pro-pcb` 克隆需要共享同一套映射；多来源优先级会增加“改了不生效”的排查成本
- `repos.*.path` 相对工作区目录解析，缺省为仓库键名，同一份配置适配多个克隆
- 配置可以包含多个本地工作区的仓库；当前工作区缺失的条目在检测时跳过
- `/gitflow:init` 默认只更新当前仓库条目，`--all` 扫描父目录下全部兄弟仓库；未扫描条目原样保留
- 配置是个人文件，不提交 Git；需要团队共享时，各成员在本地生成相同映射

`claude-lab deploy gitflow` 只部署命令、技能与文档，不创建或更新配置文件。

#### 5. 提交按固定流水线

用户明确要求：`git add -A` → 格式化 → mojibake-fixer → 再次 `git add -A` → commit-draft → commit → push。

- 先 add 让格式化工具看到完整变更范围
- 格式化后再 add，保证格式化结果进入提交
- commit-draft 生成 Conventional Commits 信息，单号从分支名与会话 ONES 内容提取
- 默认 push；`--no-push` 可只提交
- v0.4 不跑 TS 类型检查与单元测试；配置 `commit.checks` 预留数组位，未来按项目启用时只改配置

#### 6. 格式化独立成 `format-keeper`

格式化是可独立运行、也可内嵌的步骤，做成技能而非命令：

- 需要按项目检测工具、按扩展名分组、区分 `skipped` / `failed`
- `/gitflow:commit` 只引用其规则与状态，不复制实现
- 同时支持 `/format-keeper` 手动执行

#### 7. 上游跟踪修复

从远端环境分支创建任务分支时使用 `git checkout --no-track -b`。若不加 `--no-track`，任务分支会跟踪环境分支，`git push` 可能被 `push.default=simple` 拒绝，或误推向环境分支。首次 push 由 `/gitflow:commit` 使用 `git push -u origin HEAD` 建立正确上游。

#### 8. 冲突只预检，不解决

- `/gitflow:sync`：真实 merge；冲突停摆，保留冲突状态，由用户决定解决或 `merge --abort`
- `/gitflow:merge`：`git merge-tree --write-tree --name-only` 只读模拟，不碰工作区；有冲突只报告文件，不创建 MR
- 不提供 ours/theirs 自动选择：跨版本冲突方向往往需要业务判断

#### 9. 停摆优先

以下情况一律停摆并给出选项，不猜测、不重试、不绕过：

- 工作区不干净、进行中的 merge/rebase、detached HEAD
- 配置缺失/非法、环境不确定、环境分支不存在
- 工单解析失败、类型无法确定、同名分支已存在
- 冲突、push 被拒绝、glab 不可用、状态与预期不符

停摆报告必须说明：发生了什么、哪些动作未执行、可选方案。

#### 10. 多仓库协同分三层，全部显式触发

多仓库是常态而非异常，但“自动跨仓库操作”风险高，因此拆成三层：

1. **遗漏检测（默认）**：commit / sync / merge 开头只读扫描其他配置仓库的未提交改动与同名任务分支，命中即停摆提醒。改动最小、防事故价值最大；纯提醒，用户确认后可继续。报告区分「正在同名任务分支」（更强信号）与「仅存在同名分支」。
2. **`--repo <name>`**：命令显式操作配置中的某个兄弟仓库，内部用 `git -C`，会话不切目录。不自动切换、不自动选择。
3. **`--repos <a,b,c|all>`**：`/gitflow:start` 为兄弟仓库创建同名对齐任务分支（同环境、同单号），用 `git branch --no-track` **只创建、不切换**，避免改变其他仓库工作区与上下文；工作区不干净只提醒，不阻断建分支。

多仓库改动靠工单号关联，不引入额外元数据。

#### 11. `/gitflow:init` 创建与增量更新

5 个常用仓库 × 3 个环境 = 15 条映射，手写易错。初始化命令：

- 默认只扫描当前仓库；`--all` 扫描当前仓库根目录父级下的直接子仓库
- 只写 `~/.claude/gitflow.json`：文件不存在则创建，已存在则**增量更新**本次涉及的仓库条目
- 未传 `--envs` 时：首次从当前仓库远端分支自动探测环境链；已有 `chain` 则沿用并提示新增/疑似移除的环境
- 单仓库 init 不主动删除链级环境；`--all` 才基于全部目标仓库的映射证据给出删除建议；已有配置时新增环境不会自动加入 `active`
- 每个仓库一次 `git ls-remote --heads`；现有映射仍存在时优先沿用，不重复询问；否则按 `<仓库>/<环境>`、`<环境>` 候选自动匹配
- 非同构分支名（`pro-api/0.3`）无法自动匹配时**停摆询问**，不猜测
- 保留未扫描的仓库条目与未知手工字段；失效的环境键移除并在摘要中列出
- 先展示草稿与变更摘要，人工确认后落盘；支持 `--dry-run`

#### 12. 配置路径以“工作区目录”解析

v0.1 的 `path` 相对当前仓库根目录解析，多仓库配置在不同仓库内执行会得到不同结果。v0.4 只保留全局配置后：

- base = 工作区目录（当前仓库根目录的上一级）；不能使用配置文件所在目录，否则 `path: "pro-ui"` 会在 `~/.claude` 下解析
- `path` 缺省为仓库键名（`<workspace>/<repo-name>`）；标准兄弟布局可省略
- 配置版本保持 `2`；旧版本明确停摆并提示用 `/gitflow:init` 重新生成
- 同一份全局配置在任意仓库内执行命令都能解析出相同的工作区路径，不随当前目录变化

#### 13. merge 先 fetch 再比较，预检注明快照

- `fetch` 提前到推送状态校验之前，避免 remote-tracking 快照过期导致“本地与上游一致”的误报
- `merge-tree` 预检基于 fetch 时点的目标分支，报告注明 `<remote>/<env> @ <hash>`，并提示服务端合并时目标分支可能已前进

#### 14. 文档收敛与 glab 适配

- 各命令的“停摆条件”只列命令特有项，通用项引用 core §2/§5，遵守“core 单一规则来源”
- `/gitflow:sync` 的方向统一表述为“环境分支 → 任务分支”，避免读反
- glab：内网 GitLab 需 `--hostname` / `GITLAB_HOST`；描述优先用临时文件 + `--description-file`（以 `--help` 为准），规避 Windows 多行引号转义；手动入口的 Web URL 由 `git remote get-url` 按规则推导并对分支名 URL 编码

#### 15. 内嵌技能继承操作仓库上下文

`format-keeper`、`mojibake-fixer`、`commit-draft` 默认以“当前目录所在仓库”为工作对象；`--repo` 模式下会话当前目录可能不是操作仓库。core §2.6 规定调用时显式继承 `<root>`：

- git 命令一律 `git -C <root>`；`npm run` / `lc-build` 在 `<root>` 下执行
- mojibake-fixer 显式传入 `<root>` 下的变更文件绝对路径
- commit-draft 的信息收集命令替换为 `git -C <root> ...`
- 不依赖上一条命令的 `cd` 状态

#### 16. 全面改名 `gitflow`（v0.3.0 破坏性变更）

套件、技能、命令命名空间、配置文件名与全局键统一为 `gitflow`：

- 套件目录 `suites/gitflow/`，共享技能 `gitflow-core`
- 命令落入 `commands/gitflow/`，调用 `/gitflow:init` 等；manifest 映射 `commands/gitflow/*.md` → `~/.claude/commands/gitflow/`
- 配置统一为 `~/.claude/gitflow.json`（v0.4.0 进一步收敛为唯一全局文件，见决策 17）
- 旧名 `/git-flow-*`、`.claude/git-flow.json`、`gitFlow` 不再识别；v0.3 尚未部署，无迁移成本

改名动机：套件名、命令前缀、技能名、配置名此前各用一套写法（`git-flow` / `git-flow-*` / `gitFlow`），使用者需要在多种形态间换算。统一为单个词 `gitflow` 后，目录、命令命名空间、技能名与配置键一一对应，也避免了命令文件平铺在 `commands/` 根目录。

#### 17. 配置来源收敛为唯一全局文件（v0.4.0）

用户实测后澄清：只希望维护一份 `~/.claude/gitflow.json`。在 `pro-ui` 内运行 `/gitflow:init` 应只新增/更新 pro-ui 条目；`--all` 才扫描父目录下全部仓库。项目/工作区目录不应出现配置，也不存在优先级；`claude-lab deploy gitflow` 不管理配置。

v0.4.0 的选择：

- 唯一路径 `~/.claude/gitflow.json`；删除项目/工作区配置、`settings.json#gitflow` 默认值与 `GITFLOW_CONFIG` 覆盖
- `/gitflow:init` 默认单仓库、`--all` 扫描兄弟仓库；已存在时增量更新，保留未扫描条目与手工字段
- base 固定为工作区目录，`path` 缺省仓库键名；配置可以跨多个本地工作区复用
- 配置可包含当前工作区没有的仓库：遗漏检测与 `--repos all` 跳过缺失条目；显式 `--repo` / `--repos` 指定缺失仓库仍停摆
- 代价：不能再用项目配置做单项目覆盖；团队共享不再自动，需各成员本地生成；克隆目录名不同会新增独立条目
- `claude-lab deploy gitflow` 只部署命令、技能与文档，不创建或更新 `~/.claude/gitflow.json`

#### 18. 环境链自动探测与漂移提示（v0.4.0）

固定示例链（曾写作 `3.1,3.2,4.1,4.2,dev`）会随环境演进过时——新增 `5.1`、下线 `4.2` 后文档与实际不符。v0.4.0 让 `/gitflow:init` 从远端分支推断：

- 未传 `--envs` 时：首次无 `chain` → 从当前仓库远端分支探测 `<仓库键>/<env>` 与裸 `<env>` 候选；已有 `chain` → 沿用并提示漂移
- 排序：版本号按数字升序；非版本环境按内置常见顺序；`dev` 默认置顶
- 漂移：新增环境给出插入位置建议；疑似移除需满足「无任何目标仓库有效映射 + 至少一个仓库曾配置且分支消失 + 不在当前仓库候选集」
- 单仓库 init 不主动删除链级环境，`--all` 才基于全部目标仓库给出删除建议；证据不足一律保留
- 已有配置时新增环境不自动加入 `active`（首次初始化没有既有 `active`，仍等于探测出的 `chain`）；移除环境从 `active` 剔除，`default_env` 回退到 `active` 最后一项
- 显式 `--envs` 完全跳过探测与自动增删；探测只覆盖两类命名，`release/4.1` 等需显式指定
- 所有链级增删都在草稿摘要中展示，人工确认后落盘

### 与现有模块的关系

- `format-keeper`：提交流水线的格式化步骤
- `mojibake-fixer`：提交流水线的乱码检查步骤
- `commit-draft`：提交信息生成
- `ones-parser`：工单解析（优先使用）
- `gitflow-core`：本套件共享规则

### 已知限制（v0.4.0）

- `/gitflow:merge` 只创建任务 → 所属环境的 MR，环境链提升（`/gitflow:promote`）尚未提供
- `commit.checks` 仅预留，不执行
- 自动创建 MR 依赖 `glab`；不可用时只能给出手动入口
- 跨仓库写操作必须显式 `--repo`/`--repos`，不自动切换其他仓库工作区、不隐式写入
- 遗漏检测会读取所有配置仓库的 `git status`；仓库多时有一定开销，且可能提醒与当前任务无关的改动（用户确认后可继续）
- 冲突不自动解决
- Git 需 ≥ 2.38（`merge-tree --write-tree`）
- 唯一配置假设各本地工作区的仓库目录布局一致；目录名不同时，在该克隆运行 `/gitflow:init` 会新增独立条目
- 配置是个人文件，不随团队同步；团队共享需各成员本地生成相同映射
- 不再支持项目级覆盖；删除仓库或改目录名后，旧条目不会被自动清理，需手工删除
- `/gitflow:init --all` 只扫描当前工作区的直接子仓库，不递归嵌套仓库
- 环境链自动探测只识别 `<仓库键>/<env>` 与裸 `<env>` 分支；`release/4.1` 等带额外层级的分支需显式 `--envs` 与映射
- 单仓库 init 不删除链级环境；环境下线后需 `--all` 或显式 `--envs` 才能从 `chain` 移除
- 链级删除若与未扫描仓库的 `envs` 冲突会停摆，需先更新对应工作区或手工修正
- 已有配置时新增环境不自动加入 `active`，首次使用前需传 `--active` 或手工编辑
- 版本号排序假设数字版本顺序；非版本环境依赖内置常见名列表，未知命名可能排序不符合预期
- 已合并分支清理未自动化；依赖 GitLab `mr.remove_source_branch` 与合并后自动删除
