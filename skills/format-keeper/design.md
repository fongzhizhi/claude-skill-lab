# design.md

## format-keeper 设计

### 背景

`git-flow` 的提交流水线需要“先统一格式，再检查乱码/类型/测试，最后提交”。格式化是其中相对独立、可复用的一步：它既要在提交前自动执行，也要能单独手动跑。仓库已有 `style-keeper`（TS 命名/魔法数字/结构）和 `mojibake-fixer`（乱码），但前者目标更广、后者职责不同，缺少一个**纯格式化**的执行者。

### 关键设计决策

#### 1. Skill 而非 Command

- 需要按项目检测工具、按扩展名分组、区分 `skipped` / `failed`，存在多分支判断，适合 Skill。
- 需要被 `/git-flow-commit` 内嵌引用；Skill 的 `SKILL.md` 可作为规则单一来源，避免在命令里复制一套格式化逻辑。
- 同时支持 `/format-keeper` 手动触发，满足独立运行需求。

#### 2. 项目驱动，不替项目做决策

格式化工具与配置是项目级决策。本技能只读取项目已有配置/脚本，不创建、不修改、不安装。这样做的好处：

- 不会把个人偏好强加给团队仓库
- 不会因为 `prettier --write .` 造成全仓库 diff
- 没有工具的项目也能正常走提交流程（`skipped` 不阻塞）

#### 3. 只格式化目标文件

默认范围是本次 git 变更文件，手动模式可指定文件/目录。所有命令都必须带目标文件列表；检测到仓库级脚本时，替换为底层工具 + 目标文件，而不是直接执行脚本。这是防止“格式化把整个仓库重排”的核心红线。

#### 4. `failed` 与 `skipped` 分离

- `failed`：工具存在/配置存在但执行失败（语法错误、配置错误、权限、路径问题）→ 调用方停摆
- `skipped`：项目没有可用工具，或目标文件没有匹配工具 → 调用方继续并记录警告

这个区分让 `/git-flow-commit` 能“失败即停”，又不会因为项目未配置格式化而无法提交。

#### 5. 与 style-keeper 的边界

`style-keeper` 的工具兜底步骤会跑 ESLint/Prettier，但它同时做命名、魔法数字、结构治理。`format-keeper` 只做纯格式化，不碰语义与命名。未来可以让 `style-keeper` 的“工具兜底”步骤引用本技能，保持单一来源；当前不做跨模块改动，避免一次迭代范围过大。

### 与现有模块的关系

- `style-keeper`：风格治理；本技能是其格式化步骤的潜在复用点
- `mojibake-fixer`：乱码修复；格式化后如出现乱码，交由它处理
- `commit-draft`：commit message 生成；本技能不提交
- 未来 `git-flow` 套件：`/git-flow-commit` 按“add → format → mojibake → add → commit-draft → commit → push”调用

### 已知限制（v0.1.0）

- JS/TS 覆盖 Prettier/ESLint/Biome；其他语言按项目文件检测，未覆盖全部 formatter
- 无法安全限定文件范围的自定义 `format` 脚本不执行，报告后回退到配置检测
- Windows 下超长文件列表按 50 个一批；极端路径/编码场景待实测
- 不做格式化配置的初始化与迁移
