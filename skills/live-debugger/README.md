# live-debugger

> 埋点数据驱动的前端 bug 排查：快速定位数据流转关键节点 → console.log 埋点（明细公告、位置透明）→ 浏览器复现（默认人工，AI 自动按需）→ 读取 console 数据 → 收敛闭环直至修复。

前端定位 bug 最快最准的方式是 debugger——看调用栈判断流程是否符合预期，看数据判断状态是否符合预期。本技能把这个人工过程自动化：重复执行"埋点 → 复现 → 看数据 → 收敛"循环，一步步缩小范围直到根因，修完后自动清除埋点并输出根因与修复方案报告。复现环节默认为**人工复现**（AI 负责打开/刷新页面与自动取数，用户按操作清单手动执行——最快最稳、无卡点；实测 AI 自动操作浏览器慢且易出错，因此仅作可选加速）；只有用户明确要求时才用 AI 自动复现，受阻后降级交回人工。

核心哲学：**埋点数据是主要信息来源，代码分析只服务于选埋点位置**（禁止深度分析）；**复现是每轮必做的验证动作**（默认人工，自动仅按需、受阻显式降级）；**埋点对用户透明**（插入即公告位置明细，可人工确认）；**AI 复现通过 ≠ 修复完成**（收尾前由用户亲自确认）。

## 功能 / 内容

- bug 三要素前置：复现步骤、现状（问题）、预期——缺哪项问哪项，"预期"是收敛基准
- 复现方式默认人工：AI 打开/刷新页面 + 自动取数，用户按操作清单手动复现，无卡点
- AI 自动复现按需启用：仅用户明确要求且步骤简单时（快照最小化，尝试 2 次未触达即降级人工）
- 埋点透明化：插入埋点即公告 `文件:行号 | context | 变量`，附人工查看口诀（DevTools 过滤 `live-debugger`），收尾公告清除范围
- 埋点格式 `console.log('[live-debugger][<context>]', { vars })`，支持精确过滤与清除

## 使用

- **自动触发**：对话中出现前端 bug 描述，要求"定位/调试/排查/修复"问题时使用。
- **手动调用**：`/live-debugger`，附上 bug 三要素：复现步骤（含测试环境与操作序列）、现状（问题）、预期（可选 URL）。

核心约定：

- 前置三要素：复现步骤、现状、预期缺一不可；复现步骤描述质量决定复现效率
- 复现默认人工：AI 打开/刷新页面并列出操作清单，用户执行后回复确认词；想要 AI 自己操作时明确说"你自动操作"即可（仅限简单步骤）
- 埋点统一使用 `console.log('[live-debugger][<context>]', { vars })` 前缀格式；插入埋点必须公告明细（文件:行、context、变量），收尾公告清除范围
- 硬性限额：每轮排查 Read ≤ 3 / Grep ≤ 5，禁止通读文件/深挖调用链——代码分析只服务于选埋点位置
- 编译不等待：最多检查一次编译输出 mtime，严禁反复检查与 sleep 等待，编译是否生效由埋点数据出现与否验证
- AI 自动复现受阻必须显式降级人工，不静默跳过；AI 复现通过 ≠ 修复完成，收尾前请用户亲自确认
- tab 复用：navigate 优先复用已有空白 tab，不另开新 tab；若实现导致新开 tab，导航后关闭多余空白 tab，只保留目标页面一个 tab
- 默认页面 URL：`http://localhost/editor?cll=debug`（用户提供时优先；未提供直接打开默认地址并告知用户，不询问、不阻塞）
- 人工查看口诀：F12 / Ctrl+Shift+J 打开 DevTools → Console → 过滤 `live-debugger` 实时查看埋点日志
- 收尾自动清除全部埋点、保留修复代码，输出根因 + 修复方案报告

示例：`/live-debugger "编辑器里上传图片后缩略图不显示，点完上传按钮就没有反应"` → 确认三要素 → 快速定位埋点位置 → 埋点并公告明细 → 打开/刷新页面 → 用户按清单人工复现（或按需 AI 自动）→ 读取数据 → 收敛闭环至修复 → 用户最终确认。
