# feedback

## 反馈记录

### 2026-09-12（实测 v0.3.0）

用户反馈"AI 埋点后读不到数据"时常常误判，读不到数据一般有三种情况：

1. **埋点代码未更新**：没编译好、没引用当前仓库代码、缓存问题——统一总结为代码未更新
2. **埋点错误**：代码已更新但操作后根本没触发——一种是操作错误，一种是埋点本身有问题
3. **工具问题**：环境没问题、代码更新了、埋点位置也没问题、甚至控制台已打印——明显是 CDP 等读取环节出问题

现状 AI 常以为情况 1，花大量时间检查编译/环境，但有时恰恰是埋点本身的问题。用户建议：除链路关键位置外，在操作必进之路（页面加载初始化阶段）埋点并携带埋点版本信息，快速判断"代码是否未更新"。

→ 已修复（v0.3.1）：哨兵埋点——每轮必埋页面必进之路 `[boot]` 点（携带轮次号 r1/r2…，页面一加载即打印，出现 = 本轮代码已生效）；步骤 5 新增哨兵优先三分诊断链（哨兵在 → 埋点未触发，禁止查编译；哨兵不在 → 代码未更新，单次处理；哨兵不在但用户肉眼可见 → 取数链路故障，换回贴日志）；埋点格式统一带轮次号。

### 2026-09-07（实测 v0.2.0）

用户实测新版本（playwright 自动复现默认）后的反馈：

1. **AI 操作浏览器特别慢**：默认 playwright 全量快照 + 逐步确认，代价远高于人工点几下
2. **频繁操作错误**：AI 按 ref 操作经常点错、做错，需要纠错重来；人工复现虽然每轮要动手，但基本没有卡点、很迅速
3. **埋点不透明**：AI 能读到埋点数据，但用户不知道埋点位置在哪，人工无法确认——无法人机交叉验证

→ 已修复（v0.3.0）：复现方式默认反转——人工复现为主（AI 负责打开/刷新页面 + 自动取数，用户按操作清单复现），AI 自动复现降为按需启用（仅用户明确要求且步骤简单，快照最小化、尝试 2 次即降级）；埋点透明化——插入即公告明细（文件:行号 | context | 变量），给出 DevTools 过滤查看口诀，收尾公告清除范围。

### 2026-09-01（功能需求）

用户反馈技能"十分好用"，但每次都要人工复现有点麻烦。提出：引入 Playwright MCP 替代人工复现步骤，并在调用时明确 bug 三要素（复现步骤、现状、预期）；Playwright 无法操作时再降级请求人工。

→ 已实现（v0.2.0）：AI 自动复现优先（playwright 首选，snapshot + ref 确定性交互），bug 信息前置明确三要素；复现步骤分层（简单自动执行/复杂请求描述或交回人工）；自动复现受阻显式降级，不允许静默跳过；闭环保留人工最终确认（AI 自动复现通过 ≠ 修复完成，自动复现只覆盖描述路径）。

### 2026-08-18（实测两次）

用户实测两次调用后的反馈：

1. **流程分析耗时过长**：技能重点应是"根据埋点分析问题"，却花费大量时间在分析代码上
2. **编译等待耗时过长**：检查编译是否完成很久，10s 的限制对 AI 没有时间约束力
3. **未打开浏览器**：两次调用都没有打开浏览器，最基本的验证操作未执行

→ 已修复（v0.1.1）：核心哲学前置（埋点数据驱动、代码分析只辅助）、限额收紧（Read ≤ 3 / Grep ≤ 5）并禁止深度分析、编译等待改为"不等待用数据验证"、浏览器验证强制化（每轮必做，找不到 MCP 工具必须明确告知并询问，禁止静默降级）。

### 2026-08-19（实测）

用户未提供页面地址时，技能没有打开默认地址。

→ 已修复（v0.1.2）：根因是 SKILL.md 文案歧义——"（未提供用默认值）"与加粗"缺失则先询问"在同一句并存，模型跟随了更强的"询问"分支。现把 URL 明确划为可选项并写死行为：未提供 → 直接打开默认地址并告知用户，不询问、不阻塞。

### 2026-08-21（实测）

打开浏览器空白页后，再打开指定或默认 URL，空白页不会被自动关闭——期望是"直接在空白页上打开链接"或导航后空白页自动清理。

→ 已修复（v0.1.3）：根因是 SKILL.md 未规定浏览器 tab 的复用与清理策略，navigate 行为随各 MCP 实现而异（chrome-devtools 在当前活动 tab 导航，playwright 在当前 page 或新建），可能出现"另开 tab 导航、空白 tab 残留"。现规定：导航优先复用已有空白 tab，不另开新 tab；若实现导致新开 tab，导航后检查 tab 列表并关闭多余空白 tab，保证只保留目标页面一个 tab。
