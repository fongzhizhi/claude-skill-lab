# design.md

## live-debugger 设计

### 背景

前端 bug 定位最有效的手段是人工 debugger：打断点看调用栈（流程是否按预期走）、看变量（数据状态是否符合预期），逐步收敛到根因。这个过程完全可以自动化：浏览器控制 MCP（如 chrome-devtools MCP）已能打开/刷新页面、读取页面 console，配合代码埋点即可复现"看代码 → 埋点 → 复现 → 看数据 → 再埋点"的人工循环。

### 关键设计决策

#### 0. 核心哲学：埋点数据驱动，代码分析只辅助

前端 bug 排查的时间成本主要消耗在"读代码建立理解"上，而 AI 没有时间概念，一放开就会无限读。因此本技能的哲学是：**埋点数据是主要信息来源，代码分析只回答"埋点什么、埋在哪"**，不回答"为什么"——原因交给数据回答。所有流程设计（限额、编译策略、浏览器验证）都服从这一哲学。

#### 1. 为什么用 Skill 而非 Command

排查是多轮带分支的循环流程（定位 → 埋点 → 编译 → 页面 → 取数 → 收敛），不是一次性 prompt 模板；且含多个分支判断（热更新 vs 手动编译、MCP 是否有 read console 工具、修复方案是否明确）。SKILL.md 可承载完整流程与防御性边界，Command 只能承载单次指令。

#### 2. 为什么用 console.log 埋点，而不是 MCP 断点调试

- **最快**：一行 log 无需任何调试协议细节，改代码保存即可；MCP 侧只需"读取 console"一个通用能力
- **用户可主动观察**：用户复现时能实时看到日志输出，数据是否更新一目了然，与"编译是否成功"相互印证
- **与编译判定天然耦合**：log 是新代码的一部分，其出现/不出现本身就是编译生效与否的证据

断点方案需要调试协议、暂停流程、逐帧取数，自动化复杂且脆弱，收益不匹配。

#### 3. 统一前缀 `[live-debugger][<context>]`

- **可识别**：所有埋点一眼可辨，与业务日志区分
- **可过滤**：取数时按前缀精确过滤，不污染分析
- **可精确清除**：收尾按前缀 grep 删除，不误删业务日志——这是闭环能"恢复现场"的保证

#### 4. 硬性限额：Read ≤ 3 / Grep ≤ 5，且禁止深度分析

AI 没有时间概念，不设限可能无限读文件。实测反馈"流程分析很久"后收紧限额并明确禁止行为：**禁止通读文件、禁止深挖调用链全貌、禁止为"确认理解"而读代码**——代码分析的唯一产出是埋点位置。达到上限强制转入"以功能入口、数据流转关键位置为疑点"的兜底策略，保证排查必然推进到下一阶段。迭代轮数同样设无收敛保护（连续 3 轮无新信息即停下报告），防止死循环。

#### 5. MCP 工具名运行时发现，不硬编码

不同用户的浏览器 MCP 服务名不同（chrome-devtools / playwright / puppeteer），工具前缀形如 `mcp__<server>__<tool>`。SKILL.md 规定用 ToolSearch 以实际工具名为准，避免写死工具名导致不可用。

#### 6. 编译判定策略：不等待，用数据验证

项目形态决定等待方式：dev server 热更新直接跳过（保存即生效）。手动编译则**最多检查一次**编译输出目录文件 mtime 与埋点保存时间，不确定就当编译成功——**严禁反复检查、严禁 sleep 等待**（实测反馈 AI 无时间概念，反复等待编译耗时长）。编译是否生效由埋点数据是否出现来验证：数据没出现 = 编译没生效，闭环时提醒用户触发编译。等待本身没有信息量，数据才有。

#### 7. 修复策略：尽量不询问

埋点取证优先于询问：方案不明时继续缩小范围，多数情况下证据链会收敛出唯一稳妥方案；仅在方案差异显著、必须用户定夺时才询问。这与"最终完全修复再确认方案"并行不悖——减少打断次数本身就是效率。

#### 8. meta.json 软依赖的原因

浏览器 MCP 是 Claude Code 的 MCP 服务而非外部 CLI，无法用 `check` 命令安装或修复，只能检测配置是否存在。故声明 `required: false`：检测不到只提示配置方式，不拦截部署（降级为手动复现模式也能用）。

#### 9. 浏览器验证强制化：不静默降级

实测两次调用均未打开浏览器——原因是原实现"找不到 MCP 工具 → 降级为手动模式"给了 AI 静默跳过浏览器验证的出口。修正为：**打开/刷新浏览器是每轮必做的验证动作**，未打开/未读到埋点数据即不算完成一轮（写进防御性边界）；找不到 MCP 工具时必须**明确告知用户并询问**（配置后继续 or 手动降级），不允许静默降级。降级是用户的决定，不是 AI 的偷懒出口。

#### 10. 默认 URL 是可选项：永远不为此询问

实测反馈"未告知地址时没有打开默认地址"。根因是文案自相矛盾：同一句里"（未提供用默认值）"与加粗的"缺失则先询问"并存，模型面对歧义时行为不可预测，这次跟随了更强的"询问"分支。修正为把 URL 明确划为可选项并写死行为：未提供 → 直接打开默认地址并告知用户，永远不为此询问。教训：**规则类文案必须无歧义**，任何"两个指令都能解读通"的位置都是模型行为的不可控点。

#### 11. Tab 复用：不留空白页

MCP 连接浏览器后通常自带一个空白 tab（about:blank / 新开页）。各 MCP 的 navigate 行为不同：chrome-devtools 在当前活动 tab 导航，playwright 在当前 page 或新建——实现差异导致实测出现"空白页未被复用，导航后留下多余空白 tab"的残留问题。规则：**navigate 优先在已有空白 tab 上导航，不另开新 tab；若所用实现导致新开 tab，导航后检查 tab 列表并关闭多余空白 tab，保证一轮结束时只保留目标页面一个 tab**。这是"打开/刷新为每轮必做"的补充——页面存在形态也受控，避免 tab 堆积干扰用户复现观察。

#### 12. bug 信息三要素：复现步骤、现状、预期

人工 debugger 循环成立的前提是"知道往哪收敛"：复现步骤定义操作路径，现状定义实际结果，预期定义收敛基准。v0.2.0 起前置阶段明确要求三要素，缺哪项问哪项——**"预期"是本次新增**：它让"问题已修复"有了可判定的标准（复现后数据与预期相符），也让步骤 5 的分析多出一个分支（数据与预期一致但问题仍在 = 复现路径未覆盖问题场景，需换路径），避免"修完仍复现不出现场"的假收敛。

#### 13. AI 自动复现优先，人工复现降级为兜底

原流程中"用户执行操作 + 回复确认词"是每轮必做的串行人工环节，实测反馈"每次都要人工复现有点麻烦"。v0.2.0 起复现环节改为 **AI 通过浏览器 MCP 自动执行优先**，人工仅在自动复现受阻时介入。选 Playwright MCP 为首选工具：其无障碍快照机制（每元素唯一 ref、约 200-400 token/快照）比 chrome-devtools 的全 DOM/截图更适合"按步骤操作页面"，交互确定、无"点错位置"歧义。设计约束：

- **自动优先但不硬试**：复现步骤分层——简单步骤（导航/点击/输入）AI 直接执行；复杂步骤（登录态、验证码、文件上传、多步业务流）请用户描述清楚或直接声明"交回人工"，避免 AI 在自动化边缘情况空耗多轮（最多尝试 2 次即降级）
- **受阻显式降级**：沿用"不静默降级"原则（见决策 9），受阻必须告知用户并请求二选一（补充步骤重试 / 交回人工复现）
- **禁止盲点盲输**：自动复现的页面操作必须基于 snapshot 实际元素（ref），杜绝凭猜测操作

#### 14. AI 自动复现通过 ≠ 修复完成

自动复现只覆盖"用户描述的操作路径"；用户真实操作中可能存在未描述的变化（不同数据条件、不同入口、时序差异）。因此闭环保留强制的人工最终确认步骤——AI 复现数据符合预期后，请用户亲自走一遍复现步骤确认。这是三要素收敛链的最后一道闸：AI 证明"描述的路径没问题"，用户证明"真实路径没问题"。

#### 15. meta.json 与工具优先级同步更新

v0.2.0 起 playwright 为首选浏览器 MCP（决策 13）。检测时发现原有 `check` 脚本只扫描 `~/.claude.json` 与 `~/.mcp.json`，漏掉 `~/.claude/settings.json` / `.claude/settings.json`（含 local 变体）——而 settings.json 正是 Claude Code 配置 MCP 的主流位置（用户实测本地 chrome-devtools 配在此处仍报"未安装"）。**修复：check 脚本补充扫描用户级与项目级的 settings.json / settings.local.json**，服务名匹配才判为已安装。install 文案明确推荐 playwright 配置（快照省 token、ref 确定性交互）。chrome-devtools / puppeteer 仍为兜底：能找到就用，能操作的元素照常自动复现，操作不了的按"复现策略"降级。

### 与现有模块的关系

- 无其他模块依赖；与 `commit-draft`（修复完成后提交）可自然衔接
- 部署形态为单模块 skill，`dist/` 镜像结构与 skill-forge 模板一致
