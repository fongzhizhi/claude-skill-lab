# month-log-summary 设计文档

## 目标

给 month-log（手写任务行 + 脚本统计）补齐第三层：AI 主观总结。公司每月需要月总结汇报，脚本产出纯数据表格（总工时/类型分布/环比/未完成任务），人工基于数据组织叙述既费时又麻烦（用户 8-28 甚至专门登记了"月度工作整理"1h）。本 skill 把"组织语言"这一步交给 AI：阅读月总结数据、周总结、月计划与任务记录，生成约 300~500 字、先数据后结论的「AI月总结」，按 OKR 月报三段式（平时表现 / 常规工作 / 自我评价）写回文档末尾。

## 设计决策

### 模块形态：skill

- 需要携带较长撰写规则，单文件 command 承载吃力
- 触发自然：对话中"帮我生成月总结"即可命中 description
- 用户明确指定 skills 实现

### 输出结构对齐 OKR 月报三段式（v0.3.0）

用户的实际用途是每月 OKR/月报复盘，提交时按「一、平时表现 / 二、常规工作 / 三、自我评价」三段填写。v0.2.x 按工时占比分节的叙述结构需要用户二次拆解重组，"方便直接复制"的诉求没有真正满足。v0.3.0 将输出固定为三段式：

- **平时表现**：节奏（总工时 / 周均 / 单周区间）+ 协同投入（会议、协助、日常、公共投入）；
- **常规工作**：任务总数 + 各类型数量/工时/占比 + 关键结果（已完成事项）；
- **自我评价**：数据肯定（产出结构 / 完成率）+ 数据找问题（未完成项、高耗时项、预估偏差）+ 下月行动。

设计取舍：

- **标题与顺序固定，不做可选模板**：用户的目的是零加工复制，多一种变体就多一次判断成本；三节标题逐字写死在 SKILL.md。
- **评价段必须有数字锚点**：延续"主观性上限"，"稳定/饱和/产出健康"等判断必须紧跟可核对数字；"耗时超预估"只在任务行存在 `预估工时` 时成立，避免无依据归因。
- **周均分母取"有记录周数"**：自然周数会把月初/月末无记录周算进分母，拉低均值并造成"不饱和"的误判。
- **总工时允许在「平时表现」与「自我评价」各出现一次**：前者陈述事实，后者作为评价锚点，符合用户历史汇报习惯。
- **`###` 小节不影响脚本**：已核对 month-log `locateSections` 只识别 h2/h4/h5 标题与 SCRIPT 标记，三段式标题不会被误判为周总结区。

### 案例取舍：提炼规则，不写案例原文

初版曾把用户两个历史汇报（6 月、7 月）原文写入 SKILL.md 作风格锚点。审视后移除，改为提炼后的撰写规则 + 中性结构模板：

- **误导风险**：内嵌的个人非标准案例会被 Claude 当作"样板"照搬句式与结构，而每月数据形态不同（类型分布、占比、事项粒度都在变），照抄反而僵化；
- **可取之处**：案例的篇幅感、"先数据后结论"的叙述顺序、"占比小的类型合并到一句话"的处理方式，是可迁移的风格特征——已全部提炼进撰写规则（v0.3.0 起为三段式结构，篇幅约 300~500 字）；
- 结构模板用中性占位描述（平时表现 → 常规工作 → 自我评价），不携带用户具体工作内容。

### 仓库定位：全局命令反查，失败即询问

用户省去手动传路径的诉求 → 通过 month-log 的 `npm run link` 全局命令反查仓库：

- `npm root -g` 拿全局 node_modules → `realpathSync(<全局>/month-log)` 解析链接到真实仓库根（实测 Windows junction 可解析，输出 `D:\MyWorking\github\month-log`）；
- 选 `npm root -g` 而非解析 cmd shim：npm 全局根路径跨平台稳定，无需关心 shim 细节；
- 定位失败（未 link）→ 直接询问用户路径 + 提示 `npm run link`，不做其他猜测式降级。

### 默认月份：复用 month-log 的跨月周归属

month-log 的 `ownerMonthOf`：周一~周日按各月占用天数判定，平分归周一所在月（init 建文档同理）。skill 的"当月"沿用同一规则，保证"什么都不说"时的默认行为与仓库 init 一致（边界例：2026-08-31 周一，该周 8 月仅 1 天 → 默认 9 月）。月份解析自洽：归属月为上界，"上个月" = 归属月 -1，"X 月"直接解析。内置一条 node 命令确定计算，避免自然语言歧义。

### 只做单向生成，不做交互引导

"AI 提问 → 用户补写 → 合成"的交互式方案本期不做：用户诉求是"脚本缺乏主观总结、人工组织麻烦"，先解决叙述生成这一个痛点；交互引导留作二期选项（待议）。

### 覆盖即最新（无保留策略）

章节已存在则从标题到文件末尾整体替换。理由：文档在持续迭代（数据更新、换模型），历史总结无保留价值；用户明确要求"有则直接覆盖、不用询问"。git 有历史可追溯。

### 零侵入：不碰 SCRIPT 区

month-log 脚本只管理 `SCRIPT:START/END` 标记区（update 幂等写回、clear 可清空）。AI 总结写在 SCRIPT 区外的独立章节，与脚本互不干扰。skill 是纯消费者：不改 index.js、不依赖脚本 API，只读文档 + 写回一个章节。

### 不写解析器，靠自然语言读数据

月总结表格、任务行、计划都是结构化 Markdown，Claude 直接读即可提取；写专用解析器是过度工程。数字一致性靠 SKILL.md 的"数据纪律"约束（只取文档中的数字、允许约整）。

### 主观性边界

AI 总结的素材上限 = 文档已记录的信息。设计上不追求"编造洞察"，而是把文档里的事实组织成有叙事的汇报文字（归因限于文档内可见事实，如"缺陷为主因兼容性问题集中"）。计划条目在数据中无对应记录时平实带过，不虚构过程。

## 写回策略

- 章节标题：`## AI月总结`（与 `## 月总结` 同级，月总结是文档最后一个章节，故 AI 章节位于文档末尾）
- 章节内固定三个 `###` 小节：`### 一、平时表现` / `### 二、常规工作` / `### 三、自我评价`，便于整段复制到 OKR 系统
- 已存在：匹配标题行（忽略首尾空白的精确行匹配，避免误伤正文提及），从该行到文件末尾整体替换
- 不存在：清理末尾多余空行后追加
- 不改动任何其他内容

## 风险与待议

- 章节位置约定（文档末尾）依赖用户不再往后追加内容；若实际使用中发现用户常在末尾手写补充，可改为 `AI:START/END` 双标记包裹（对齐 SCRIPT 方案）
- 月总结数据区缺失时 skill 提示先跑 `node index.js update`；非 month-log 格式文档一期直接拒绝生成并说明原因
- 仓库定位依赖全局 link；若用户在其他机器未 link，流程退化为询问路径，属预期降级
- 三段式的措辞（小节标题、加粗标签）目前写死；若用户后续的 OKR 系统模板变化，需同步修改 SKILL.md 的「固定结构」
- 二期候选：交互式引导补写（"本月最大的困难是什么"）、生成周报/述职多体例、多个月份批量生成
