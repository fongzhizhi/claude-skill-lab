# design.md

## comment-keeper 设计

### 背景

仓库已落地 TS 注释规范：`rules/ts-standards`（强制规则）+ `docs/ts-code-guide`（详细指南）。规则只覆盖新增/修改的代码，存量代码的注释大概率不符合规范。需要一个工具批量对齐存量注释，且不依赖人工逐文件 review。

### 关键设计决策

#### 1. 为什么用 Skill 而非 Command

- 需要按 600+ 行的详细指南执行，Skill 可明确指引加载参考文档；Command 只是 prompt 模板，不适合承载"读文档 → 逐节核对"的多步骤流程
- 流程含分支判断（四种范围模式、结构调整触发条件），Skill 的 SKILL.md 可承载完整判断逻辑
- 未来可挂 references/ 扩展（如审查清单、反模式速查表）

#### 2. 范围策略：默认 git diff，支持手动指定

默认取 git diff 变更文件，符合"改动随代码走"的实际工作流——新改动集中在 diff 中，一次调用即可覆盖。手动指定（函数/文件/目录）覆盖存量代码批量迁移场景。函数模式只处理该函数上下文，避免误伤无关区域。

#### 3. 行为等价铁律

结构调整（提取函数、改名、拆分）仅在与代码行为严格等价时执行。原因：注释调整是低风险操作，而结构重构可能引入行为差异；宁可只改注释，也不冒行为变化的风险。结构调整的触发条件全部引用指南原文依据（子分隔符暗示提取、命名不清优先改名）。

#### 4. 不虚构信息

- TODO/FIXME 无负责人 → 保留原样并列入摘要待用户补充。负责人是人际信息，无法从代码推断，虚构会造成误导。
- 补录的 `BUSINESS:` / `DESIGN:` 等标签 → 只写从代码可推断的确定事实，不确定的语义不臆造。
- `@ts-ignore` / `@ts-nocheck` → 不擅自删除（删除可能暴露类型错误），只列入建议清单。指南虽禁止，但清理动作应由开发者确认。

### 与现有模块的关系

- 依赖 `docs/ts-code-guide`（指南）与 `rules/ts-standards`（规则），不重复维护规范内容，只做执行者
- 部署形态为单模块 skill，`dist/` 镜像结构与 skill-forge 模板一致
