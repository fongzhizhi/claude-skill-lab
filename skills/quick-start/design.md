# design.md

## quick-start 设计

### 背景

日常开发中经常要快速验证某个功能或新改动，但触发入口往往很深（多层菜单、特定流程前置），甚至功能还没接入口。人工验证成本高：要么一步步点界面，要么临时改代码后还要记得还原。quick-start 用自动注入测试代码的方式把"验证"这件事变快：理解诉求后选择最小侵入的注入手段，验证完精确清除，恢复原状。

### 与 live-debugger 的关系：同引擎，不同目标

两者共享同一套运行骨架——浏览器 MCP 驱动、硬性限额、编译判定、刷新页面、console 取数、闭环收敛。**区别在目标与行为**：

| 维度 | live-debugger | quick-start |
| --- | --- | --- |
| 目标 | 修复 bug | 验证功能 / 数据 |
| 注入内容 | console.log 埋点为主 | 埋点 + 快捷入口 + mock + 硬编码 |
| 行为边界 | 修复代码是持久改动，保留 | 所有注入都是临时的，收尾全清 |
| 结束标志 | 用户无法复现 bug | 数据/行为符合预期 |

因此 quick-start 不是 live-debugger 的复制，而是同一骨架上的"验证向"实例：注入手段更丰富（不止埋点），而清理要求更严格（全部注入都要还原）。

### 关键设计决策

#### 1. 注入手段选择矩阵

按验证诉求的场景选择注入手段，而不是一律埋点：入口深 → 快捷入口（减少操作步骤）；数据不可得 → mock（造数据）；状态特定 → 硬编码（固定参数）；看数据 → 埋点。**优先选改动最小、最局部的注入**——能 mock 局部数据就不 mock 整个接口，能改数据消费处就不碰请求层，降低清理风险。

#### 2. begin/end 标记对 vs 单行前缀

live-debugger 的埋点是单行 log，前缀即可精确清除；quick-start 的注入可能是多行代码块（mock 数据、快捷入口函数），单行前缀删不干净。因此多行注入用 `// [quick-start] begin: <名>` / `// [quick-start] end` 标记对包裹，清除时按对删除。两类标记统一前缀 `[quick-start]`，保证"收尾 grep 零残留"的验证手段成立。

#### 3. 可逆性原则（注入红线）

注入只替换数据、暴露入口、临时改参数，不改业务逻辑本身；清理后代码行为必须完全恢复。这条红线把"注入"与"改代码"划清界限——注入是测试动作，不是需求改动，凡是摘不干净的注入方式（与业务逻辑纠缠）一律不采用，先调整注入策略。清理不干净是这类工具最严重的事故形态，因此收尾强制 grep 验证零残留。

#### 4. 硬性限额与无收敛保护（同 live-debugger）

Read ≤ 5 / Grep ≤ 10 防止无时间概念的空转，超限兜底为入口与数据流转关键位置；连续 3 轮无新信息即停下报告，防止注入死循环。两者同为"AI 无时间概念"的结构性对策。

#### 5. MCP 工具名运行时发现，不硬编码

与 live-debugger 相同：不同用户的浏览器 MCP 服务名不同（chrome-devtools / playwright / puppeteer），工具前缀形如 `mcp__<server>__<tool>`，运行时以 ToolSearch 实际结果为准。

#### 6. meta.json 软依赖

浏览器 MCP 是 MCP 服务而非外部 CLI，无法用 `check` 命令安装，只检测配置是否存在；`required: false`，缺失时降级为手动复现模式，不拦截部署。

### 与现有模块的关系

- 与 `live-debugger` 共享运行骨架约定（硬性限额、编译判定、标记规范、MCP 软依赖），文档相互对照
- 部署形态为单模块 skill，`dist/` 镜像结构与 skill-forge 模板一致
