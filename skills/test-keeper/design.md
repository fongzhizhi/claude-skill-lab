# design.md

## test-keeper 设计

### 背景

仓库已落地 TS 测试规范：`rules/ts-standards`（含强制规则 `ts-testing.md`）+ `docs/ts-code-guide`（含详细指南 `ts-testing-guide.md`）。规则约束新增测试，但存量代码的测试要么缺失、要么注水（只测恰好路径、Mock 被测模块自身、快照断言等）。需要一个工具按规范**补充缺失测试、修复注水测试**，并与既有 OpenSpec 工作流（openspec-propose）衔接：改动量大时先出方案、改动小时直接优化。

### 关键设计决策

#### 1. 为什么用 Skill 而非 Command

与 comment-keeper 同因：需要按 200+ 行详细指南执行（Skill 可明确指引加载参考文档），流程含多分支判断（范围判定 → 无测试/有测试 → 问题多/少 → propose/直接优化），且需要嵌套调用 openspec-propose 技能。Command 只是 prompt 模板，承载不了这种多步骤决策树。

#### 2. 范围策略：git diff 归并业务模块，手动指定兜底

与 comment-keeper 不同：注释调整的对象是"diff 变更的文件"（文件级），而测试是"模块级"存在（一个模块一个/一组测试文件）。因此 git diff 变更文件先**归并到业务模块**（源码根下首层目录），判定唯一模块后才进入审查；多模块或无法判定时由用户指定。测试文件定位按 同目录 → `__tests__/` → `tests/` → vitest/jest include 的优先级查找。

#### 3. 双分支决策树：无测试走方案，有测试走门禁

- **无测试** → 自动启动 openspec-propose 编写方案（用户需求明确"无需二次确认"），复用既有 OpenSpec 工作流的 planning boundary——只产出规划工件，不落地代码，等待用户预览执行。openspec CLI 缺失时降级为三选一提示（安装 / 初始化仓库 / 直接手写）。
- **有测试** → 按指南第八章"质量门禁"审查。红线（注水、Mock 被测模块自身、大型组件快照、异步漏 await）一票否决，常规问题逐项计类，量化阈值：红线 ≥1 或常规 ≥3 类 = 问题很多。

#### 4. 分级处理：问题多报告、问题少直接优化

- **问题很多**（改动风险大）→ 输出问题清单 + 改造方案，提示用户是否走 `/opsx:propose`（change name `fix-tests-<模块>`）。用户拒绝 → **仅输出报告不动手**（用户已确认此回退路径），避免未授权的大范围改动。
- **问题不多** → 直接优化并总结结论，符合"问题小则快速闭环"的效率诉求。

#### 5. 行为边界：只改测试，不动源码

测试优化过程中发现的**源码缺陷只记录、不代修**——测试的使命是锁定契约，修复源码缺陷是另一个动作（且可能需按 Bug 驱动流程：先写复现用例红 → 修源码绿）。覆盖目标行 ≥80%、重点 branches，严禁追求 100%（指南明确最后 20% 为负收益）。

#### 6. 不虚构信息

与 comment-keeper 一脉相承：补测试时不臆造业务规则——不确定的输入/输出语义优先询问用户或从代码推断确定事实；不擅自定义"应该有的行为"作为断言。

### 与现有模块的关系

- 依赖 `rules/ts-standards`（`ts-testing.md` 强制规则）与 `docs/ts-code-guide`（`ts-testing-guide.md` 详细指南），不重复维护规范内容，只做执行者
- 复用 `suites/openspec` 的 `openspec-propose` 技能 / `/opsx:propose` 指令，不自己实现 OpenSpec 工件生成
- 与 comment-keeper 互为姊妹技能（注释 vs 测试），结构、元技能约束、部署形态完全一致
