# AI 辅助自动化测试方案（未来研究）

> 本文档记录 `claude-skill-lab` 在自动化测试与 Skill 评测方面的架构思考，**属于未来研究方向，非当前开发任务**。随时跟进，随项目演进持续更新。

---

## 背景与问题

### 现状痛点：MCP + AI 直接操作浏览器

当前主流方案是 **MCP + AI** 逐步操作浏览器（如 Playwright MCP，live-debugger 已在用）：

| 问题 | 表现 |
|------|------|
| **Token 消耗大** | 每步操作都要把页面快照发给 LLM |
| **执行速度慢** | 每步都要等 LLM 推理 |
| **结果不确定** | 同一输入，每次执行的路径可能不同 |
| **成本高** | 每次执行都产生 API 费用 |

### 传统自动化的局限

传统 Playwright 脚本虽然快（0 token、毫秒级），但：

| 问题 | 表现 |
|------|------|
| **脆弱** | DOM 结构一变就挂 |
| **维护成本高** | 流程一变就得重写 |
| **不理解语义** | 只认选择器，不认意图 |

### 核心洞察

> **两者混合是最优解：稳定的部分让自动化脚本执行，不稳定的部分让 AI 分析。**

AI 应该从"执行者"变成"维护者"。执行是确定性的、低成本的；维护是需要理解力的、高价值的。Token 用在刀刃上。

**本仓库语境下的"刀刃"**：只有 `evals/` 首次生成脚本与失败诊断两个环节消耗 token，其余全部零 token。

## 适用前提与边界

> 为什么标记为"未来研究"：本方案有两个硬性前提，当前项目尚未具备。

### 前提条件

1. **被测试项目集成了测试/可执行环境**（单元测试框架或可按脚本驱动运行的入口）——没有可执行环境，脚本层无从落地
2. **目标场景以 E2E / 集成测试为主**（有页面、有接口、有可观测行为）——纯单元测试场景下 AI 价值极低，`test-keeper` 已覆盖

### 适合 / 不适合场景

| 场景 | 结论 | 原因 |
|------|------|------|
| 有稳定 PO 层 / 页面结构的大项目 | ✅ 适合 | 脚本层收益最大，AI 维护成本摊薄 |
| 有 CI 门禁的回归测试 | ✅ 适合 | 回归模式 0 token，天然适合门禁 |
| Skill 的自动化评测（本仓库） | ✅ 适合 | 见下「与 claude-skill-lab 的结合」 |
| 快速原型、一次性验证 | ❌ 不适合 | 脚本层建设成本 > 直接 MCP 操作 |
| 纯单元测试 | ❌ 不适合 | test-keeper 更贴场景 |

**部署成本提示**：第一层（项目本身改造：语义化标签 + 结构化埋点）需要**改造被测试项目**，这是全方案中成本最高、最难启动的一步。实操中应允许"无埋点降级"：脚本层先跑通，埋点渐进补齐，AI 诊断依赖降级为截图 + DOM 快照。

## 架构设计

### 三层分工

```
┌─────────────────────────────────────────────────────┐
│  AI 层（维护者）                                     │
│  职责：分析代码、编写脚本、诊断失败、迭代优化        │
│  介入时机：仅在需要理解、决策、诊断时               │
│  Token 消耗：低（只在维护层）                       │
├─────────────────────────────────────────────────────┤
│  自动化仓库（执行者）                                │
│  职责：封装操作 API、执行测试脚本、捕获结果          │
│  介入时机：每次测试执行                              │
│  Token 消耗：零                                     │
├─────────────────────────────────────────────────────┤
│  项目本身（被测试对象）                              │
│  职责：业务逻辑 + 语义化标签 + 结构化埋点            │
│  介入时机：开发者日常迭代                            │
│  Token 消耗：零                                     │
└─────────────────────────────────────────────────────┘
```

### 各层详细设计

#### 第一层：项目本身

**目标**：让自动化脚本和 AI 都能稳定、准确地识别元素和理解行为。

**1. 语义化 DOM 标签**

```html
<!-- 差：AI 看不懂这是干嘛的 -->
<button data-test="btn-1">提交</button>

<!-- 好：AI 能理解语义 -->
<button data-test="submit-order">提交订单</button>
```

原则：
- 标签命名使用业务语义，而非位置或序号
- 使用 `data-test` 前缀，与业务属性隔离
- 关键交互元素必须带标签
- （可选）命名规范设计见[待办](#待办与跟进)，命名风格应对齐项目已有的 `data-test` 使用情况，避免双规范共存

**2. 结构化埋点**

```javascript
// 差：自由文本，AI 需要解析
console.log('用户登录成功，耗时 320ms');

// 好：JSON 格式，AI 直接读取字段
console.log(JSON.stringify({
  event: 'login_success',
  duration_ms: 320,
  user_id: 'u123',
  timestamp: Date.now()
}));
```

原则：
- 使用 JSON 格式，字段名语义化
- 记录关键事件、耗时、上下文信息
- 便于自动化脚本捕获，便于 AI 分析
- **生产声噪问题待解**：浏览器端 `console.log` 混入业务日志，建议固定前缀（如 `[evt]`）或走统一上报通道，见[待办](#待办与跟进)

#### 第二层：自动化仓库

**目标**：封装稳定的操作 API，让测试脚本易于编写、执行和维护。

**1. Page Object 模式**

```javascript
// 自动化仓库中的 API
class LoginPage {
  async goto() { ... }
  async login(username, password) { ... }
  async expectWelcome() { ... }
}

class OrderPage {
  async goto() { ... }
  async submitOrder() { ... }
  async expectSuccess() { ... }
}
```

原则：
- 每个页面/模块封装为独立类
- 对外暴露语义化的方法，隐藏选择器细节
- AI 生成新脚本时，只需组合已有 API（"组合优于生成"——生成的选择器是新的债，组合 QA API 是复用）

**2. 版本同步 —— 可选形态，重量待定**

```
项目 v1.2.0 → 自动化仓库 v1.2.0
项目 v1.3.0 → 自动化仓库 v1.3.0
```

原则：
- 版本一一对应：Git submodule / 版本标签 / monorepo workspaces 三选一
- 避免"脚本对应旧版页面"的问题
- **个人 / 小团队场景不必独立仓库**：脚本头部声明适用版本 + 运行日志记录实际版本，即可轻量解决对应问题；独立仓库 + submodule 是为多团队长期项目准备的重量方案，作为可选演进而非必选

**3. 独立仓库**

自动化测试代码放在独立仓库中，与项目仓库解耦：
- 项目仓库专注业务逻辑
- 自动化仓库专注测试脚本
- 通过 API 或 CLI 交互
- ⚠️ 同上：**个人场景可降级**为项目内 `tests/e2e/` 目录，先跑通再谈解耦

#### 第三层：AI 层

**目标**：在需要理解和决策时介入，维护脚本、诊断问题。

**介入场景**：

| 场景 | AI 行为 |
|------|---------|
| 首次测试 | 分析项目代码 → 生成测试脚本 |
| 脚本失败 | 分析失败原因 → 更新脚本 |
| 新增功能 | 分析新代码 → 生成新测试用例 |
| 结果分析 | 读取结构化埋点 → 生成评测报告 |

**不介入场景**：

| 场景 | 执行者 |
|------|--------|
| 日常回归测试 | 自动化脚本 |
| 重复执行 | 自动化脚本 |
| 简单断言 | 自动化脚本 |

**失败诊断分级（进一步省 token）**：不是一失败就请 AI，而是三级递进——

```
① 断言失败 → 重跑一次 + 埋点上下文（多数是时序/数据问题，脚本级解决）
② 规则化自愈 → 重试、刷新、扩大等待、选择器回退（写在脚本里，0 token）
③ 仍失败 → AI 介入，喂"结构化失败包"（脚本 + 日志 + DOM 快照）
```

与 live-debugger 的"哨兵三分诊断"同源，都是"先定域，再上 AI"。

### 执行流程

```
首次测试：
  AI 分析项目代码 + 自动化仓库 API
    ↓
  生成测试脚本（存入自动化仓库）
    ↓
  脚本执行（0 token）
    ↓
  AI 分析执行结果，生成报告

日常回归：
  脚本执行（0 token）
    ↓
  通过 → 输出结果
    ↓
  失败 → 诊断分级（① ② 脚本级，③ 才上 AI）
    ↓
  AI 更新脚本，重新执行——更新后的脚本回流仓库，下次就是 0 token
```

## 与 claude-skill-lab 的结合

### 评测 Skill 的双模式设计

| 模式 | 执行方式 | 适用场景 | Token 消耗 |
|------|---------|---------|-----------|
| **探索模式** | AI + MCP 逐步执行 | 首次评测、未知 Skill | 高 |
| **回归模式** | 确定性脚本快速执行 | 日常回归、CI 门禁 | 零 |

> 探索模式与 `live-debugger` 现有路径（AI 自动复现 + Playwright MCP）天然重合，首版可复用，不必新造。
> `test-keeper` 管"项目单元测试"（在项目内），本方案管"Skill 自身评测"（在本仓库），两者互补不重叠。

### 评测工作流

```
1. 读取 skills/<name>/evals/
2. 有现成脚本 → 直接执行（0 token）
3. 没有脚本 → AI 分析 Skill 代码，生成脚本
4. 执行脚本，捕获：
   - 操作序列是否成功
   - console 埋点数据
   - 最终输出
5. AI 分析执行日志，输出评测报告
6. 脚本存入 evals/scripts/，供下次复用
```

### 评测目录结构

```
skills/<name>/
├── evals/
│   ├── config.yaml          # 评测配置
│   ├── cases.yaml           # 测试用例定义
│   ├── scripts/             # 生成的自动化脚本
│   ├── fixtures/            # 测试数据（静态快照）
│   └── reports/             # 历史评测报告
```

### 测试数据来源

| 数据 | 谁提供 | 说明 |
|------|--------|------|
| `cases.yaml` | Skill 开发者 | 必须写，定义测试场景 |
| `fixtures/*` | Skill 开发者 | 静态快照，可复现 |
| `scripts/*` | AI 生成 + 人工审查 | 首次生成后复用 |

## 风险与开放问题

| 风险 | 说明 | 缓解方向 |
|------|------|---------|
| **脚本也会过时** | 脚本 = 二次债，版本同步不解决"选择器失效"本身的诊断成本 | 语义化标签 + 失败分级诊断 + 自愈规则 |
| **第一层改造门槛** | 语义化标签 / 埋点要动被测试项目，未必有权改 | 提供无埋点降级（截图 + DOM 快照），埋点作为增强 |
| **评测对象可能非浏览器** | Skill 不只是前端套路，CLI / 文件型 Skill 无 DOM 可打 | 评测脚本抽象为"操作序列 + 断言"，底层实现可换（浏览器 / CLI / 文件对比） |
| **独立仓库运维负担** | submodule / 版本同步在个人场景是纯负担 | 标注为可选演进，首版用模块内 `evals/scripts/` 即可 |
| **AI 诊断质量** | 失败包给不全 → AI 瞎猜 | 失败包最小要素沉淀为规范（脚本 + 日志 + 快照三件套） |

## 演进路径

| 阶段 | 目标 | 具体动作 | 对 claude-skill-lab 的意义 |
|------|------|----------|---------------------------|
| **第一阶段** | 手动 + AI 混合 | 人工写核心脚本，AI 辅助生成边缘脚本 | 先给 1 个 skill（如 commit-draft）加 evals/ |
| **第二阶段** | AI 生成 + 人工审查 | AI 生成所有脚本，人工抽查关键路径 | 落定 cases.yaml schema，普及到全部 skill |
| **第三阶段** | AI 自维护 | AI 自动检测脚本失效并修复 | 集成 feedback.md 自动追加评测结果 |
| **第四阶段** | 预测性维护 | AI 根据项目代码变更，提前更新脚本 | 依赖自动化仓库与项目版本对应关系成熟 |

当前处于**第一阶段到第二阶段的过渡期**（尚未开始）。

## 关键设计原则

1. **Token 用在维护层，不在执行层**：执行时零 token，只在写脚本和分析结果时消耗 token
2. **AI 做决策，脚本做执行**：AI 负责理解和决策，脚本负责快速重复执行
3. **语义化优先**：DOM 标签、埋点数据都要语义化，便于 AI 理解
4. **版本同步**：自动化仓库与项目仓库版本一一对应（个人场景可轻量降级）
5. **渐进式信任**：从人工审查到 AI 自维护，逐步提升自动化程度
6. **失败分级上 AI**：先脚本级自愈，后 AI 诊断，平时零成本
7. **组合优于生成**：AI 写新脚本时组合已有页面 API，少开新选择器
