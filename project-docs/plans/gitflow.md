# Git Flow AI 化构思文档

> 本文档记录一套基于环境分支模型的 Git 工作流，以及用 AI 提升效率的设计构思。核心哲学：AI 只负责正常流程的重复劳动，异常情况停摆或交给人。


## 一、设计哲学

### 核心原则

> **AI 只负责正常流程的重复劳动，异常情况停摆或交给人。**

具体表现：

| 原则 | 说明 |
|------|------|
| 正常流程自动执行 | 创建分支、同步、提交、建 MR，不打断 |
| 偏离即停 | 遇到不在预设流程内的情况，立即停止，输出状态和偏离点，询问用户 |
| 不猜测、不修复 | 不尝试"聪明地"绕过问题，不做自动修复 |
| 特殊情况人工处理 | 异常场景不值得让 AI 花时间判断，人工解决更快 |
| 迭代优化提示词 | 同一停摆场景反复出现，说明是常见场景，优化提示词；只出现一次的，人工处理即可 |

### 为什么这样设计

- 多场景判断会让 AI 不断思考，效率反而低下
- 异常处理逻辑越复杂，AI 的行为越不可预测
- 人的判断力在异常场景下远优于 AI，没必要让 AI 勉强处理


## 二、Git 工作流模型

### 模型定位

本模型是 Git Flow 的变体，称为 **"环境分支模型"**。

标准 Git Flow：

```
master（生产） ← develop（开发集成） ← feature / release / hotfix
```

本模型：

```
环境分支（长期、保护、对应具体版本环境，链式包含）
  ├── dev           集成分支（最高版本）
  ├── 4.1
  ├── 3.2
  └── 3.1

任务分支（短期、个人命名空间、可自由 push）
  ├── {user}/feat/{version}-{ticket}   需求
  └── {user}/fix/{version}-{ticket}    bug 修复
```

### 关键特征

| 特征 | 说明 |
|------|------|
| **链式包含** | 高版本包含低版本，改动从低版本向高版本流动 |
| **多版本并行** | 3.1、3.2、4.1、dev 同时存在 |
| **保护分支** | 所有环境分支受保护，禁止直接 push，必须走 MR |
| **跳级合并** | 改动可一次合入多个高版本，不强制逐级 |
| **任务分支从低版本拉** | 从目标环境分支创建，不跨版本复用 |

### 分支策略

| 类型 | 命名 | 生命周期 |
|------|------|---------|
| 需求 | `{user}/feat/{version}-{ticket}` | 从创建到 MR 合并 |
| Bug 修复 | `{user}/fix/{version}-{ticket}` | 从创建到 MR 合并 |

**默认一个任务一个分支**。AI 消除了分支管理成本后，独立分支的劣势消失，优势保留（分支即任务、状态清晰、无需 cherry-pick、无长期分支同步问题）。

低优先级 bug 可选聚合到批次分支，但这是可选项，不是默认。


## 三、阶段划分

整个开发流程分为三个阶段：

```
┌─────────────────┐    ┌─────────────────┐    ┌─────────────────┐
│   环境准备       │ →  │   开发提交       │ →  │   合并           │
│                 │    │                 │    │                 │
│ /git-start      │    │ /git-commit     │    │ /git-merge      │
│ /git-sync       │    │                 │    │                 │
└─────────────────┘    └─────────────────┘    └─────────────────┘
```

三个阶段既有关联，又相互独立。用户只面对四个命令，内部逻辑不暴露。


## 四、通用前置检查

### 所有 Git 操作前的统一检测

任何会改变分支或工作区状态的操作，执行前必须先检测工作区状态：

```
git status --porcelain
```

| 输出 | 含义 | AI 行为 |
|------|------|---------|
| 空 | 工作区干净 | 继续执行 |
| 有已暂存改动 | `git add` 过但未提交 | 停摆 |
| 有未暂存改动 | 改了但未 add | 停摆 |
| 有未跟踪文件 | 新文件未纳入版本控制 | 停摆（但需区分是否属于本次任务） |

### 停摆后的选项

不替用户决定，列出选项让用户选：

```
⚠️ 当前工作区有未提交改动：
  M  src/components/ColorPicker.tsx
  ?? src/utils/color.ts

请选择：
  [1] 先提交（调用 /git-commit）
  [2] 暂存改动（git stash）
  [3] 放弃改动（git checkout -- . / git clean）
  [4] 手动处理后再继续
```

选 [4] 时，AI 完全退出，用户处理完重新调用命令。

### 未跟踪文件的特殊判断

`??` 状态的文件不一定要停摆：

| 情况 | 处理 |
|------|------|
| 本次任务新增的源文件 | 属于正常改动，应该纳入提交 |
| `.env.local`、日志文件、构建产物 | 应该被 `.gitignore` 忽略，可能没配好 |

AI 的处理：**列出未跟踪文件，询问用户是否纳入本次提交或加入 `.gitignore`**，而不是一刀切停摆。

### 各命令的前置检查

| 命令 | 需要检查工作区 | 原因 |
|------|--------------|------|
| `/git-start` | ✅ | 切分支会带走未提交改动或冲突 |
| `/git-sync` | ✅ | merge 前不能有未提交改动 |
| `/git-merge` | ✅ | 切换分支做预检会受影响 |
| `/git-commit` | ❌ | 本身就是处理改动的 |


## 五、环境准备阶段

### `/git-start`：创建任务分支

**用户入口**：

```
/git-start PRO-159115【冒烟测试】显示颜色设置背景色之后，重新打开PCB，背景色丢失
heep:ones.lceda.com/project/#team/TkSb58GQ/issue/PRO-159115
4.1环境的缺陷
```

**内部流程**：

```
1. 通用前置检查：工作区是否干净？
2. 解析 ones 单 → 提取工单号（PRO-159115）
3. 读 git 用户名（git config user.name → jiangshun）
4. 推断环境：
   - 用户明确说"4.1" → 用 4.1
   - 用户没说 → 从上下文推断
   - 无上下文 → 默认 dev
5. 查仓库-环境映射（.claude/env.json）
   → 4.1 对应 pro-ui/4.1
6. 判断分支是否已存在：
   - 自己创建的 → 问："是否切换到该分支继续开发？"
   - 别人创建的 → 停摆，报告冲突
7. 执行：git checkout -b jiangshun/fix/4.1-PRO-159115 origin/pro-ui/4.1
```

**产物**：分支名 `jiangshun/fix/4.1-PRO-159115`

**停摆条件**：

- 工作区有未提交改动
- ones 单解析失败
- 环境无法确定且无默认值
- 同名分支被他人创建
- 目标环境分支不存在

### `/git-sync`：同步迭代分支

**用户入口**：

```
/git-sync 4.1
```

**内部流程**：

```
1. 通用前置检查：工作区是否干净？
2. git fetch
3. 检测当前分支是否落后于目标环境分支（git log 对比）
4. 如果有新提交，执行 git merge origin/pro-ui/4.1
5. 如果有冲突 → 停摆，列出冲突文件
6. 如果无冲突 → git push
```

**为什么做成 skill**：价值在"检测是否落后、检测未提交改动、检测冲突"三个判断点，不在 git merge 本身。

**停摆条件**：

- 工作区有未提交改动
- merge 冲突
- push 被拒绝（权限或保护分支）


## 六、开发提交阶段

### `/git-commit`：格式化 + 检查 + 提交 + 推送

**用户入口**：

```
/git-commit              # 完整流程（默认包含 push）
/git-commit --quick      # 跳过测试和 TS 检查
/git-commit --no-push    # 只提交，不推送
```

**内部流水线**：

```
1. 检测仓库配置 → 决定启用哪些步骤
2. 格式化（有配置则执行，无则跳过）
3. 检查项（快速失败的先跑）：
   ├─ 乱码检测（/mojibake-fixer 的检测逻辑）
   ├─ TS 类型检查（有 tsconfig.json 则执行 tsc --noEmit）
   └─ 单元测试（package.json 有 test script 则执行）
4. /commit-draft 生成 commit message
5. git commit
6. git push（默认包含，--no-push 可跳过）
```

**步骤启用规则**：

| 步骤 | 检测依据 | 执行方式 |
|------|---------|---------|
| 格式化 | `.prettierrc` / `.eslintrc` / `package.json` 的 `format` script | 有则执行，无则跳过 |
| 乱码检测 | 始终执行 | 始终 |
| TS 类型检查 | `tsconfig.json` | 有则执行，无则跳过 |
| 单元测试 | `package.json` 的 `test` script | 有则执行，无则跳过 |

**顺序原则**：先改代码（格式化），再查代码（检查项），最后提交。

**失败即停**：

| 失败步骤 | AI 行为 |
|---------|---------|
| 格式化失败 | 停，报告错误 |
| 乱码检测发现乱码 | 停，列出文件，提示运行 `/mojibake-fixer` |
| TS 类型报错 | 停，列出错误 |
| 单元测试失败 | 停，列出失败用例 |
| commit-draft 失败 | 停，问用户手动写 message |

**不包含代码审核**。本地代码审核 skill 默认不跑，因为慢且主观，不适合每次提交都跑。


## 七、合并阶段

### `/git-merge`：创建 MR + 冲突预检

**用户入口**：

```
/git-merge              # 合当前环境，然后询问是否合高版本
/git-merge +dev         # 合当前环境 + dev，不问
/git-merge --no-ask     # 只合当前环境，不问高版本
```

**核心逻辑**：

```
1. 通用前置检查：工作区是否干净？未推送 commit？
2. 从当前分支名解析当前环境（fix/4.1-xxx → 4.1）
3. 必选目标：当前环境分支（pro-ui/4.1）
4. 冲突预检：本地模拟 merge 到 pro-ui/4.1
   - 有冲突 → 列冲突文件，停摆
   - 无冲突 → 继续
5. 创建 MR → pro-ui/4.1（必选，执行）
6. 询问："是否同步到更高版本？可选：dev"
   - 用户选 dev → 冲突预检 → 创建 MR
   - 用户选不需要 → 结束
7. 输出汇总：所有 MR 链接
```

**关键点**：

| 点 | 说明 |
|----|------|
| **当前环境是必选** | 开发分支从 4.1 拉出，合回 4.1 是必须的，不是可选的 |
| **高版本是可选** | 默认询问用户，不自动推断"该不该合" |
| **逐个确认、逐个预检** | 一个高版本卡住了问用户是否继续下一个，不一次性处理所有 |
| **冲突预检** | 在创建 MR 之前本地模拟 merge，提前暴露风险 |

### MR 模板

在仓库的 `.gitlab/merge_request_templates/` 下放 `cross-version.md`：

```markdown
## 关联工单
{{ticket}}

## 变更说明
{{summary}}

## 合并链路
源分支：{{source_branch}}
目标分支：{{target_branch}}
本次合并为：{{merge_type}}（当前环境 / 链式同步 / 用户指定）

## 自测情况
- [ ] 本地验证通过
- [ ] 单元测试通过（如有）

## 审核人
/assign_reviewer {{reviewers}}
```

**审核人指定**：

| 来源 | 方式 | 适用 |
|------|------|------|
| 仓库级默认 | `.gitlab/CODEOWNERS` 按目录自动分配 | 所有 MR 的兜底 |
| 调用时指定 | `/git-merge --reviewer @zhangsan` | 本次合并需要特定人看 |

用户没指定时，AI 不主动 @ 具体人，只依赖 CODEOWNERS 或留空。

### 冲突处理

**AI 不解决冲突，只做预检和报告。**

预检结果分三种情况：

| 预检结果 | AI 行为 |
|---------|---------|
| 全部目标无冲突 | 继续创建 MR |
| 部分目标有冲突 | 停摆，列出"哪些目标有冲突、冲突文件是什么"，询问用户：只创建无冲突的 MR，还是全部暂停？ |
| 全部有冲突 | 停摆，报告冲突概况，建议用户手动处理或改用 cherry-pick 方式 |

**预检报告内容**（只读，不执行）：

- 冲突文件列表
- 每个文件的冲突类型（内容冲突 / 删除冲突 / 重命名冲突）
- 如果冲突范围很小（如仅版本号、import 路径），提示"可能是机械冲突，建议人工确认"

**不提供"ours/theirs 自动选择"选项**，因为跨版本合并的冲突方向往往需要业务判断，自动选边风险太高。


## 八、多仓库处理

### 核心原则

> **跨仓库修改是"需要用户确认的常见场景"，不是异常。AI 停摆询问，用户确认后为另一个仓库创建对齐版本的任务分支；合并时各仓库独立执行。**

### 处理流程

```
当前在 pro-ui 仓库开发，发现需要改 pro-pcb
  ↓
AI 停摆，输出：
  "检测到需要修改 pro-pcb 仓库，当前工单 PRO-159115。
   是否为 pro-pcb 创建对应的任务分支？"
  ↓
用户确认 → AI 为 pro-pcb 创建分支（版本环境与 pro-ui 对齐）
用户拒绝 → AI 继续当前仓库，但提示"pro-pcb 的改动需要手动处理"
```

**不自动切仓库、不自动创建分支、不自动修改另一个仓库的代码。** 因为：

- 多仓库切换后，当前会话的上下文会混乱
- 用户可能只是"看到了需要改的地方"，还没决定现在改
- 自动创建分支后如果用户不打算改，会留下垃圾分支

### 版本对齐

```
pro-ui:  jiangshun/fix/4.1-PRO-159115
pro-pcb: jiangshun/fix/4.1-PRO-159115
```

同一个工单号，同一个版本，只是仓库不同。AI 创建时默认沿用当前仓库的版本环境，用户如果要改，显式说明。

### 关联方式

多仓库的改动靠**工单号**关联，不需要额外的元数据：

- 分支名都包含 `PRO-159115`
- MR 模板中的工单号相同
- 评审人可以通过工单号看到关联的多个 MR

### 合并时的处理

`/git-merge` 在哪个仓库执行，就只合哪个仓库。多仓库需要分别执行：

```
# 在 pro-ui 仓库
/git-merge

# 切换到 pro-pcb 仓库
/git-merge
```

**不自动跨仓库合并**。因为：

- 各仓库的合并目标可能不同（pro-ui 合 4.1+dev，pro-pcb 可能只合 4.1）
- 冲突预检需要各自在本地模拟
- 合并的时机可能不同（pro-ui 先合，pro-pcb 后合）


## 九、配置文件

### `~/.claude/gitflow.json`（唯一全局配置，v0.4 起）

配置由 `/gitflow:init` 创建或增量更新；不创建项目/工作区配置，也没有多文件优先级。

```json
{
  "version": 2,
  "chain": ["3.1", "3.2", "4.1", "dev"],
  "active": ["4.1", "dev"],
  "default_env": "dev",
  "remote": "origin",
  "repos": {
    "pro-ui": {
      "path": "pro-ui",
      "envs": {
        "dev": "pro-ui/dev",
        "4.1": "pro-ui/4.1",
        "3.2": "pro-ui/3.2",
        "3.1": "pro-ui/3.1"
      }
    },
    "pro-pcb": {
      "path": "pro-pcb",
      "envs": {
        "dev": "pro-pcb/dev",
        "4.1": "pro-pcb/4.1",
        "3.2": "pro-pcb/3.2",
        "3.1": "pro-pcb/3.1"
      }
    }
  }
}
```

**说明**：

| 字段 | 用途 |
|------|------|
| `version` | 配置版本，当前固定 `2` |
| `repos` | 仓库名 ↔ `{ path, envs }`；`path` 相对工作区目录，缺省为仓库键名 |
| `envs` | 环境名 → 远端环境分支完整名（如 `pro-ui/4.1`），不要求各仓库同构 |
| `chain` | 完整的链式顺序 |
| `active` | 当前活跃的环境（用于推断可选高版本） |
| `default_env` | 用户未指定环境时的默认值 |
| `remote` | 远端名，缺省 `origin` |

新增仓库或环境时，优先重新运行 `/gitflow:init` 增量更新配置，不改 skill。


## 十、AI 行为边界

### 可完全自动化

| 操作 | 所属阶段 |
|------|---------|
| 创建任务分支 | `/git-start` |
| 同步迭代分支 | `/git-sync` |
| 格式化、检查、提交、推送 | `/git-commit` |
| 冲突预检 | `/git-merge` |
| 创建 MR | `/git-merge` |
| 清理已合并分支 | 合并后自动 |

### 需用户确认

| 操作 | 原因 |
|------|---------|
| 合并高版本 | 用户可能只想合当前环境 |
| MR 合并 | 涉及代码进入保护分支，必须人工确认 |
| 冲突解决 | AI 给出冲突信息，用户决策 |
| 删除有未合并内容的分支 | 需确认无未处理内容 |
| 跨仓库创建分支 | 用户可能还没决定现在改 |

### 绝不自动执行

| 操作 | 原因 |
|------|------|
| 直接 push 到保护分支 | 违反团队规范 |
| 强制推送 | 破坏历史 |
| 自动合并 MR | 跳过评审 |
| 自动解决冲突 | 跨版本冲突需业务判断 |

### 停摆清单

遇到以下情况，AI 立即停止，输出状态和偏离点，询问用户：

- 工作区有未提交改动（所有 git 操作前）
- ones 单解析失败
- 环境无法确定且无默认值
- 同名分支被他人创建
- 目标环境分支不存在
- merge 冲突
- push 被拒绝
- MR 创建失败
- 需要修改其他仓库
- 任何不在预设流程内的情况


## 十一、与标准模型的对比

| 维度 | Git Flow | GitHub Flow | 本模型 |
|------|----------|-------------|--------|
| 长期分支 | master + develop | main | 多个环境分支 |
| 版本管理 | release 分支 | 无 | 环境分支即版本 |
| 多版本并行 | 不直接支持 | 不支持 | 原生支持 |
| 保护策略 | master | main | 所有环境分支 |
| 合并方式 | 本地 merge | PR | 必须 MR |
| 冲突处理 | 手动 | 手动 | AI 预检 + 人工解决 |
| 多仓库 | 不涉及 | 不涉及 | 工单号关联，独立合并 |
| 适用场景 | 定期发布的产品 | 持续部署的 Web 应用 | 多环境并行的产品 |

## 十四、实施决策（2026-11-02）

评估后确认的调整，已落地到 [suites/gitflow](../../suites/gitflow/README.md)：

| 项 | 决策 |
|----|------|
| 指令命名 | 统一使用 `gitflow:` 命名空间：`/gitflow:init`、`/gitflow:start`、`/gitflow:sync`、`/gitflow:commit`、`/gitflow:merge`，避免与 Git 原生命令混淆 |
| 环境同步 | **链式**：任务分支只合回所属环境；环境之间按 `chain` 顺序逐级 MR 提升（`4.1 → dev`） |
| 未指定环境 | 默认 `default_env`，即链式顶端（通常 `dev`） |
| 异常处理 | AI 不能快速解决的异常一律**停摆询问**，不猜测、不重试、不绕过 |
| 配置位置 | 唯一全局配置 `~/.claude/gitflow.json`：`/gitflow:init` 默认更新当前仓库，`--all` 扫描父目录下全部仓库；不创建项目/工作区配置，无多文件优先级；`claude-lab deploy` 不管理配置 |
| 提交流水线 | `git add -A` → `format-keeper` → `mojibake-fixer` → `git add -A` → `commit-draft` → `git commit` → `git push`；v0.1 暂不含 TS 检查与单元测试 |
| 格式化 | 独立为 `skills/format-keeper`，可单独运行，也被 `/gitflow:commit` 内嵌引用 |
| 分支创建 | `git checkout --no-track -b`，避免任务分支跟踪环境分支导致 `git push` 误推/被拒 |
| MR 范围 | v0.1 只创建“任务分支 → 所属环境”的 MR；环境链提升规划为 `/gitflow:promote`（P2） |
| MR 通道 | 优先 `glab`；不可用时停摆并给出手动创建入口（分支已推送时 `git push -o merge_request.create` 是 no-op，不作兜底） |
| 冲突 | 只预检不解决：sync 冲突停摆；merge 用 `git merge-tree --write-tree --name-only` 只读预检 |
